# 현재 실행부의 실제 MCP 읽기 검증

**현재 설치된 Ollama 실행부로6개 요청을 처리해 실제 MCP7회와 모델9회를 확인했다. FW 조회는 완료했지만 journal 실패·호스트 범위 확대·DNS 판단 미완료·불필요한 시각 계산이 남았다.** [결과 원장](validation.json) · [현재 현황](../../../STATUS.md). 앞선 [모델 구성요소16사례](../../../finetuning/WORKFLOW_DEVELOPMENT.md)와 구분하며 같은 문항이 있어 독립 평가로 부르지 않는다.

## 무엇을 실행했는가

- 관리자231→A→B 경유, 기존 비특권 `soc-ollama` 계정에서 현재 설치본을 새 프로세스로 import했다. 설치19소스/스킬·config SHA를 요청별 확인했고 전후 불변이다.
- 현재 모델은 `soc-qwen36:35b-balanced-q4km-20261108`, 실제 접근 프로필은 `hermes-parity`다. 도구 범위 축소·필수 읽기 선택·보정·공통 렌더러를 그대로 사용했다. 실행부가 모델9회·실제 읽기7회를 기록했다.
- 시험 프로세스에만 추가 쓰기 차단을 두었다. 보호 MCP 전에 거절하며 실제 보호 호출·차단 시도·채팅 게시·운영 소스/설정/서비스 변경·공격·학습0이다. 설치 권한을 변경하거나 일반 sudo/Docker를 봇에 위임하지 않았다.
- FW/단순 진단/시각은 좁힌 도구를 썼고, rule-worker·DNS 요청에는45도구가 노출됐다. 단일 허용 도구라도 target enum이 넓으면 질문 밖 호스트를 선택할 수 있었다.
- 03:21의 두 봇 heartbeat/worker·두 채팅 서비스/자동 조사 타이머와 대기열0을 읽었다. 03:26 GET만으로 Ollama·공동 검토·경보 채널이 공개이고 모델 manifest digest가 `7ac2a1dc6aa17746f522e81804ba2a76b25fc01e69d2460a083a0ec5cfa207c3`임을 관측했다. 이 digest는 새로22GB 가중치 파일을 전수 해시한 값이 아니다.

질문의6개 라이브 추적은 사용한 개발 자료다. 새 기관 사건 정답·독립 평가 세트로 편입하지 않는다. 실제 반환 본문/SHA·완료 상태와 의미 검토를 따로 보관했다. Hermes·두 봇 공동 검토·실제 채널·새 모델 비교·승인형 쓰기의 성공을 이 시험으로 대신하지 않는다. 기존19파일 정확 적용 후보도 그대로 PREPARED·승인 대기다.

## journal 원인과 보완 후보

실패 시점의 `capstone-journal-reader.service` 감사 기록은 `command_timeout`이다. 같은24시간의 severity err 조회는 약0.06초지만 warning/info의 고정 오류 정규식 검색은12초 제한에 걸렸다. 역순 검색도 같은24시간에서 제한에 걸려 채택하지 않았다. 역순15분 실험의 빈 결과 처리 오류는 옵션 위치가 고정 grep 식별을 바꾼 시험 절차 문제이며 보존·분리했다.

같은24시간을6시간씩4구간으로 나눈 관리자 읽기는 모두 성공·합계13.004초였다. 이를 합친 [journal 분할 후보](../../mcp/journal-window-slices.md)는 같은 요청에서12.638초·기존 응답 검증 통과였다. 요청 기간을 줄이거나 기존12/20초 제한을 늘리지 않았다. 후보는 기존 root core를 사용하는 격리 함수 실행이며 운영 reader/MCP·서비스 sandbox에서 적용한 결과가 아니다.

현재 공개 소스의 journal 후보와134검사는 준비됐지만 서버에는 원래 모듈이 남아 있다. 다음은 설치 사본/복구 경로·A/C의 현재 소스 대조와 정확 적용안 준비, 승인 후 reader 재시작·실MCP/새 채팅 확인이다. 코드가 준비됐다는 이유로 권한 문제나 모든 조회 실패가 해결됐다고 표시하지 않는다.

## 보존·검증 범위

결과16파일·427,636바이트와 SHA를 보존하고 감독/작업자 PID 종료·소스19/config 불변 확인 후 B 시험16파일을 제거했다. Ollama/review/journal 서비스와 자동 조사 타이머 active를 확인했으며 서비스 조작0이다. 기존 PREPARED후보·복구본·G_Harness2·자료/가중치를 유지했다. 새 하네스 코드는 수정하지 않았고 이번 진단/백엔드 후보를 Harness² 검사라고 표현하지 않는다. 호스트 범위·시각 요청의 하네스 변경은 이후 공식 Harness²→동결/회귀→정확 승인/적용→새 채팅 순서로 진행한다.
