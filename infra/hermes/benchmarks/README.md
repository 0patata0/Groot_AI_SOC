## 부분편집 비교

`compare_rule_edit.py`는 같은 22,652바이트 합성 파일과 같은 맨 앞 주석 추가 작업을 `propose_rule_edit`로 요청했다. 모델이 짧은 `old_text`/`new_text` 치환 하나를 반환하면 벤치마크 프로세스가 원본에 적용해 전체 후보를 재구성했다. 당시 `compare_write_candidate.py` 파일은 수정하지 않고 스트림 수신 코드를 재사용했다.

부분편집 응답 두 건은 같은 치환을 반환했다. 첫 줄의 끝 LF는 치환 문자열에 포함하지 않고 원문에 남겨두었으며, 재구성한 후보는 기대한 22,696바이트와 SHA까지 일치했다. 모든 규칙·주석·공백·마지막 LF를 보존했다. 기존 전체 후보 시험의 `complete_correct=false` 기록은 그대로 유지한다.

모델이 반환한 **룰 텍스트는 99.3% 감소**했지만 **전체 응답 시간 감소는 24.6%**였다. 부분편집에서도 추론 문자열이 21,327자로 관측됐고 도구 인수는 응답 종료 직전에 처음 도착했다. 긴 추론이 남았다는 관측과 시간 결과를 구분하며, 추론 본문을 저장하지 않았으므로 그 구체적인 원인은 단정하지 않는다. 문자 수를 토큰 수로 간주하거나 두 감소율을 같은 의미로 해석하지 않는다.

두 시험의 합성 파일과 요청한 변경은 같지만 도구 스키마·출력 지시와 측정 시각은 다르다. 실제 입력 토큰도 8,742와 9,004로 다르며, 서버 부하와 캐시는 통제하지 않았다. 일반적인 수정 작업의 속도나 운영 전체 처리 시간을 입증하는 결과는 아니다. 부분편집 측정 전후 모델 정보·버전·설정·태그 digest가 같고, 최종 적재 컨텍스트는 262,144였다. 최초 모델 적재 약 8.388초가 포함된 준비 요청 9.180초는 위 평균에서 제외했다. 독립 검토 당시 전송 코드와 스키마 원본 해시도 실행 시 기록과 일치했다.
