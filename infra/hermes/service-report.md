## 진단 원인 누락 수정

B의 실제 `capstone-management.service` journal에는 11/6 `status=failed`, `error=controller_already_running` JSON219건이 있었다. stderr에서 기록된 priority6은 기존 err 필터와 고정 문자열 분류 모두에서 빠져, 진단MCP에는 종료값1과 systemd 일반 오류만 나타났다. 모델은 실제 직접 원인 코드를 받지 못한 채 추가 도구를 반복 탐색했다.

진단MCP1.2.4/공통 수집기는 정확한 unit·JSON 두 키·failed·고정 코드가 모두 일치할 때만 이 오류를 분류한다. 정상적인 `status=deferred`, 다른 unit, 추가/중복 키, 인용 HTTP 본문·임의 코드를 실패로 승격하지 않는다. 코드 의미는 잠금 획득 실패이며 잠금 소유 작업의 건강성·진행을 증명하지 않는다.

B의 고정24시간 backfill은219행을 추가하고 기존664행을 바꾸거나 삭제하지 않았다. DB quick_check와 비root `mcp` 계정의 실제 MCP 조회에서 코드 전달을 확인했다. 원본journal과 보완 전 DB는 보존한다. 이는 정제 색인 보완이며 전체 journal 무손실·전체 오류 건수의 증명은 아니다. A/C에는 이번 B 전용 원인 수정의 운영 배포를 하지 않았고, 신규 설치용 canonical 소스는 공통으로 갱신했다.

## 설치와 복구

기존 단일 `deploy.sh`가 공통 contract, Native gate/query pin, SDK runtime, 진단 수집기/이력/MCP 소스를 복사하는 경로를 사용한다. 새 패키지·수신 포트·키·권한·모델·방화벽 정책을 추가하지 않았다. 새 OS 전체 설치 시험은 수행하지 않았다.100 실제 Hermes는 모델7회 합71.019초/실제5읽기, Ollama는 모델4회 합29.331초/실제2읽기 합0.129초였다. 대기·초기화·모델·MCP의 범위를 서로 대체하지 않는다.
