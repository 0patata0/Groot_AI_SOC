공통 구현은 `soc_management_run.py`의 `parse_incident_disposition`, `incident_impact_read_timestamps`, `incident_impact_missing`이다. Native root 제어기는 같은 root 참조파일을 import하고 SDK는 기존 SHA 고정 grounding 복사본을 사용한다. CLI에 포함된 실제 gate와 root 참조파일 SHA도 계속 일치해야 한다. 파일 복사본만 갱신하고 이전 포함코드를 실행하지 않는다.

SDK의 실제 센서 사건 읽기 조사에는 같은 명시적 판단·인용 계약을 적용한다. 이전에는 경보 조회 유무·일부 문장 검사만 있어 원문의 정상/종결 판단에 자산별 사건 구간 조회가 없어도 통과할 여지가 있었다. 이제 빈 표본·실패·불완전 이벤트로 positive 판정을 만들거나 실제 호출이 없는 도구를 인용하면 보정 대상이다. 메타데이터는 사설 감사에 남기고 공개 답변에서는 숨긴다. 조회 작업 완료와 실제 사건 종결은 별개다.

SDK의 연결 대응은 실제 같은 출발지의 임시차단 상태 영수증과 request/proposal ID로 확인한다. 사용자/카드 문장 자체를 승인·실행 근거로 삼지 않는다. 이는 모든 보호 쓰기·혼합 요청·SCA·상태 연계·다중 사건의 Native 전체 제어기가 SDK에 이식됐다는 뜻이 아니다. 해당 동등성은 계속 별도 검증 대상이다.

## SDK 조회 선택 보완

수정 전 SDK 실제 읽기 시험은103.682초·모델3회/실제MCP0회로 partial이었다.16개 호출 계획이 매번2048출력 토큰을 채우며 마지막 arguments가 누락됐고, 검증 거절 뒤 다음 선택에 오류가 전달되지 않아 같은 잘못된 계획을 반복했다. 모르는 agent ID도 여러 개 추정했다.

이제 선택 묶음은 최대4호출이고, 전체32도구/12모델 상한과 미조회 범위 보고는 유지한다. 전체 계획을 검증하기 전 일부만 실행하지 않는다. 다음 선택에는 누락 arguments 위치·검증 경로·선택 수/상한을 전달하며 인자 값·모델 원문은 복사하지 않는다. agent_id는 이번 요청의 SHA 검증된 등록/인벤토리나 사용자가 명시한 검색 범위로 제한한다. 알려진 ID가 없으면 unfiltered 조회 또는 실제 인벤토리/웹등록 탐색을 모델이 선택한다. 인벤토리만으로 사건 조사 완료를 인정하지 않는다.

이번 추가10검사는 잘못된 계획의 호출0·다음 선택 오류 전달·수정 계획 실제 dispatch, 묶음 상한, 날짜/IP/룰 ID와 agent 구분, 실제 등록 SHA·별도17/129 ID·변조 거절을 확인했다. 새 패키지·고정 조회/정답/agent ID 추가0이다.

## 새 운영 재검토에서 발견한 잔여

11/5 기존 DVWA 사건의 새 읽기 전용 재검토는148.766초·13호출 중9오류로 needs_review를 유지했다. `rule-b`에 `a:waf`를 전달하거나, `requested_at_kst`/`destination_ip` 같은 미지원 인자를 사용했고, agent의 과거 경보를 manager 로그 도구로 찾으려 했다. manager 로그의 필수 `level` 누락·숫자 level·반복 오류 뒤 Native의 회로 차단도 관측했다. 이를 네트워크 실제 단절로 확정하지 않는다.

새 backend 도구가 운영에 있어도 이 실행은 해당 조사까지 도달하지 못했다. 종결 검사가 보완됐다는 이유로 실제 사건 조사 성공으로 표시하지 않는다. 다음은 Native의 실제 도구 스키마/추가 인자·정확한 대상/manager와agent 조회 구분·인자 실패의 연결 장애 오분류를 고치고 다시 확인하는 일이다. 새 SDK 재시험은120.068초/모델5회·MCP6회/오류0이었다. 실제WAF/IDS·웹등록/접근·필터된Wazuh까지 읽었지만 agent별 당시 전체 경보는 누락됐고0표본·해소 단정이 거절되어 partial을 유지했다. 수정 전보다 조회는 회복됐지만 사건 종결·응답 속도 향상을 증명하지 않는다. 웹등록의 중복 조회도 남는다.

이 시험에서 SDK 실패 요약이 웹 근거를 빠뜨린 목록으로 돌아가는 경로도 확인했다. 이제 Native의 같은 factual_review_report를 사용한다. 최종 설치본에서 실제6영수증 재생으로 표·웹근거/보관잘림·내부 제어 줄 숨김을 확인했다. 이 마지막 표시 보완은 새 모델/채팅/UI 시험이 아니다.

## 운영·설치·복구

B13파일을 기존 프로필·소유권/모드·SHA 비교 후 증분 갱신했다. Native/SDK/review 실행부를 각각1회 재시작했고, 기존 35B·도구 수·MCP/승인/보호주소/TTL·모델 권한은 바꾸지 않았다. 새 패키지·이미지·포트·키·환경 설정 입력도 없다. 실제 새3VM 설치는 사용자 조건으로 실행하지 않았다.

단일 `deploy.sh`의 기존 source bundle이 common/controller/query·SDK 소스를 그대로 복사하고 초기 설치에서 root 참조파일과 CLI gate를 함께 렌더링한다. 같은 디렉터리의 root 공통 모듈을 읽는 현재 systemd 진입점과 실제 포함 SHA를 운영에서 검증했다. 기존 운영 서버에 전체 초기 설치기를 실행하지 않았다.

원본/후보/manifest·독립 복구는 `/var/lib/capstone-incident-parity/20261105-r1/deployment`에 보존한다. 활성 실행이면 복구를 미루고 본 후보 SHA와 일치하는 파일만 되돌린다. DB·승인·대화는 되돌리거나 삭제하지 않는다. 00:49:18 KST13파일·보호설정7SHA·두 봇의 새 WS/worker heartbeat·실제 gate/참조 일치를 확인해 확정했다. Native1회·SDK/review각3회 재시작했고, 독립 타이머 해제/confirmed recovery no-op을 확인했다. 실제 수동 원복은 미시험이다. 배포 도우미의 JSON 끝 문자 오류는 즉시 정정하고 manifest/영수증·전체13파일을 재검증했다. 같은 관리자231→A→B 경로에서 root가 `rollback.py --manual`을 실행하는 복구 절차다.

필요한 영수증이 있다는 것은 그 자료의 의미상 충분성·실제 자산 관계·로깅 연속성을 자동 보장하지 않는다. LLM의 상관분석·앱/호스트 영향·후속 구간·승인 경과·최초 차단 지연·전 업무 종결과 최종 논문/시연은 여전히 전체 목표의 잔여다.
