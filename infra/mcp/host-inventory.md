2026-11-08 KST. A/B/C의 `get_host_inventory`를 공통 `soc-query`와 `soc-output`에 연결했다. 조회는 승인 없이 가능하며 기존 보호 변경 승인 절차는 유지한다. 일반 셸·sudo·Docker 실행 권한을 모델에 주는 기능은 아니다.

## 공통 문맥·조회 규칙 (11/8 후속 보완)

공통 대상 해석 → 실제 등록 도구의 범위·인자 검사 → MCP 실행 → 근거/누락 검사 → 공통 표 출력 순서를 Native·SDK·review 채널이 공유한다. 특정 서비스만의 예외를 쌓지 않고 장비별 인자·반환 형식만 따로 처리한다.

| 대화 | 유지·전환 기준 |
|---|---|
| B hermes 컨테이너 → 메모리는? → 로그도 | B의 같은 Docker 이름·종류 유지 |
| A 임의의 실제 `.service` → 메모리는? → 로그도 | A의 정확한 systemd unit 유지; Docker/호스트 전체 RAM으로 대체 금지 |
| C 디스크 상태 → 메모리는? | 같은 C 호스트의 메모리 조회 |
| WAF/IDS/Wazuh 규칙 → 상세히/표로 | 장비·기본/커스텀·rule ID·상관 필터 유지 |
| FW 규칙 → input만 → 다음 페이지 | 같은 hook 범위·검증된 페이지 조건 유지 |
| Docker 조회 → 지금 관제 현황 알려줘 | 명시한 새 주제 우선, 관제 현황 새 조회 |

`관제 현황`은 `soc:coverage`, 최근60분 Wazuh 경보 최대5개 표본, 현재 `list_blocks()`를 실제 조회한다. 보고/처리/검토 대기, 호스트별 수집·서비스 점검, 동적 차단, 경보 표본을 구분한다. 표본을 구간 전체 건수·공격 성공 수로 표현하지 않는다. 과거·원인·변경·추가 필터는 이 현재 현황 조회로 축소하지 않는다.

후속 질문이 계승하는 것은 동일 사용자·확인된 대화 경계의 대상과 조건이다. 이전 봇 답변 수치·판단·승인은 계승하지 않는다. 순수 재정리만 요청하면 실제 영수증과 원관측 시각을 사용하고 새 조회 없음이라고 밝힌다. Docker 로그·상세는 이름이 없으면 한 번 확인한다.

현재 모든 loaded unit의 상태·상세는 인벤토리로 조회하지만 **journal 원문은 기존 등록된 고정 target 범위**다. 임의 unit 이름을 유지하는 문맥 기능이 모든 unit의 journal 권한을 새로 열었다는 뜻은 아니다. 미지원 대상은 다른 unit/컨테이너 조회로 대신하지 않는다.

## 공통 용량 표시

`skills/soc-output/SKILL.md`의 용량 규칙을 두 봇이 공유하고, `harness.capacity_text`가 확인된 수치와 원단위만 변환한다. 디스크·메모리·스왑·서비스 메모리·Docker 메모리/입출력에 같은 SI 단위를 사용한다.

| 원자료 | 표시 |
|---|---|
| 107374182400 bytes | 107.37 GB (107,374,182,400 bytes) |
| 16777216 KiB | 17.18 GB (16,777,216 KiB) |
| 1000000000000 bytes | 1 TB (1,000,000,000,000 bytes) |
| Docker 270.5MiB | 약 283.64 MB (270.5 MiB) |

소수점 최대 두 자리, GB=10⁹ bytes·TB=10¹² bytes다. 원본 영수증·SHA는 그대로 유지한다. 이미 반올림된 Docker 통계는 정확한 바이트 원본으로 취급하지 않으며 `약`을 표시한다. `infinity`, `[not set]`, 미확인과 CPU%·PID·카운트·시간은 변환하지 않는다. 디스크 단문은 로컬 파일시스템 목록을, 메모리·스왑 단문은 자원 조회를 선택한다. 모델이 환산값을 다시 생성하는 단계는 추가하지 않는다.
