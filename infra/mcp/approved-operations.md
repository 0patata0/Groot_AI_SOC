## 호출 경계

```text
관리자 → Hermes → rule-a / rule-b (비특권 SSH 강제 명령)
                     │
                     └─ 고정 root helper, 엄격한 JSON 요청 검증
                          ├─ 기존 룰 변경: 정확한 파일 후보 → 승인 → 검증·적용
                          ├─ 서비스 작업: 고정 대상/동작/현재 상태 → 승인 → 1회 실행
                          └─ A 임시 차단: 원본 증거 재검증 → 최대 10분 차단
                                                   └─ 유지 승인 / 해제 요청

B soc-bot /operations → Mattermost 지정 관리자 버튼
A/B 기존 rule-change-worker → 승인 1회 소비 → 실행·결과 검증·보고
```

승인은 정확한 요청 ID, 작업 종류, 대상, 계획 SHA-256, 관찰 SHA-256, 만료시각에 결속된다. 요청·응답 HMAC, Mattermost 콜백의 실제 TCP 출처, 명시적 승인자 ID와 비공개 nonce를 검증한다. LLM의 “승인받았다”는 문장이나 사용자 이름 문자열로 실행하지 않는다. 운영자는 현재 승인 카드의 버튼으로 결정한다.

| MCP 도구 | 기능 |
|---|---|
| `get_service_action_target(target)` | 현재 서비스 관찰, 허용 동작, 기준 상태 해시, 중단 영향 조회 |
| `propose_service_action(target, action, base_state_sha256, reason)` | 정확한 기준 상태에 결속된 서비스 작업 승인 요청 |
| `temporarily_contain_ip(ip, reason)` | A에서 서버측 실제 경보를 검증하고 제한된 임시 차단 요청 |
| `get_operation_status(request_id)` | 서비스/임시 차단 요청의 승인·실행·검증·만료 상태 조회 |

기존 `get_rule_change_target`·`propose_rule_change`·`get_rule_change_status`도 유지된다. 큰 룰 변경은 전체 후보를 제출하며, 검토 메시지가 여러 개여도 승인 대상은 하나의 정확한 후보다. 자세한 한도와 검토 메시지 방식은 [룰 변경 배포 문서](rule-change-deploy.md)를 따른다.

## 서비스 작업의 허용 범위

| 대상 | 서버 | 허용 동작 | 검증 요점 |
|---|---|---|---|
| `a:waf` | A의 기존 `waf` | `reload`, `restart` | nginx 설정 검사, master/worker 세대 또는 시작시각, DVWA 응답, DetectionOnly 유지 |
| `a:suricata` | A의 기존 `suricata` | `restart` | 전체 룰 검사, passive 구성, 재시작 이후 실제 룰 로드 시각과 실패·skip 0 |
| `a:chatproxy` | A의 기존 `chatproxy` | `reload`, `restart` | nginx 설정 검사, 프로세스 세대, 고정 인증서와 실제 채팅 ping 응답 |
| `b:wazuh-manager` | B의 기존 Wazuh manager | `restart` | analysisd 설정 검사, 핵심 Wazuh 프로세스 상태 |
| `b:wazuh-dashboard` | B의 기존 Wazuh dashboard | `restart` | 새 시작시각, 고정 인증서와 실제 로그인 페이지 응답 |

대상 문자열을 컨테이너 이름이나 명령으로 그대로 실행하지 않는다. 코드의 고정 프로필에서 경로·컨테이너·명령·확인 URL을 선택한다. 다른 서비스, 이미지 변경·다운로드, `docker compose up`, 컨테이너 생성·삭제·마운트/네트워크/환경변수 변경, 패키지 설치·삭제는 지원하지 않는다.

1. 현재 컨테이너 ID·이미지·시작시각·상태·마운트·관련 파일·설정 해시를 읽는다.
2. LLM이 받은 기준 해시와 최신 상태가 일치해야 제안할 수 있다. 설정 검사 전후의 상태도 다시 대조한다.
3. 승인 카드에는 대상·동작·이유·실행 전 상태 요약·검증 계획·영향을 표시한다. 승인 기한은 10분이다.
4. worker는 실행 직전 다시 설정을 검사하고 상태를 대조한다. 승인 1회 소비 후에도 기준 상태가 바뀌었다면 실행하지 않는다.
5. 실행 의도를 먼저 영속화하고 고정 명령을 한 번 실행한다. 결과가 불확실한 중단·실패에서는 자동 재실행하거나 `reload`를 임의의 `restart`로 확대하지 않는다.
6. 컨테이너·설정이 그대로인지, 새 프로세스 세대/시작시각과 실제 서비스 응답이 확인되는지 검증하고 결과를 보고한다. 전체 실행 후 관찰은 상태 조회에서 확인한다.

기존 컨테이너의 재시작은 서비스 중단을 일으킬 수 있다. 종료 유예시간은 일반 대상 30초, Wazuh manager 60초이며, 종료하지 않으면 Docker가 강제 종료할 수 있다. 이 영향도 정확한 동작의 사전 승인 범위에 포함한다. 실패 시 추가 복구 작업은 새 상태를 조회하고 별도 제안을 만들어 승인받는다.

## 공격 의심 IP의 임시 선차단

이 경로만 사용자가 미리 허용한 긴급 대응 예외다. 룰 변경과 서비스 작업은 계속 사전 승인이 필요하다. 임시 차단은 기존 `inet capstone_fw agent_block`의 단일 IPv4 원소만 조작하며, WAF 엔진 모드나 Suricata IDS/IPS 모드를 변경하지 않는다.

### 초기 자동 판정 기준

**10/13 사용자 정의 보충:** 프로젝트의 논리적 외부망은 학과 실습망이고, 내부망은 이미 구성된 `10.200.10.0/24`와 Docker 가상 NIC·네트워크 영역이다. 따라서 아래 공인 주소 전용 조건은 **현재 구현의 제한**이며 프로젝트 외부망 전체를 뜻하지 않는다. 실습 공격을 포함하려면 보호 주소와 지정 공격 호스트를 기준으로 정책을 조정해야 한다. 이번 설명 정정으로 라이브 차단 범위를 변경한 것은 아니다.

여기서 **“외부 공인 IPv4”는 학과망 소속 여부가 아니라 센서가 관측한 출발지 주소의 공인/비공인 분류와 보호 목록을 기준**으로 한다. A의 외부 인터페이스에 연결된 학과망 주소도 사설 주소라면 제외된다. 학과망 밖에서 시작했더라도 NAT 후 센서에 사설 출발지로 보이면 이 자동 경로의 대상이 아니다. DGX가 있는 `211.170.162.0/24`는 공인 주소여도 별도로 보호한다.

LLM은 IP와 사유만 전달한다. 사유 문자열, LLM이 제시한 경보 ID·건수·심각도는 차단 증거로 인정하지 않는다. A의 고정 Suricata 원본 `eve.json`과 직전 회전 파일에서 다음을 모두 확인한다.

- 최근 5분의 severity 1 공격 분류이며, 사전에 제외한 정찰·정책·기존 오탐 SID가 아니다.
- 같은 **외부 공인 IPv4 출발지**에서 A 또는 보호 내부망으로 향한 서로 다른 TCP 흐름 3개 이상이다. 동일 흐름의 여러 SID·여러 패킷은 한 흐름으로 센다.
- `ens192`, `direction=to_server`, 이벤트와 흐름의 출발지·목적지가 일치한다.
- 양방향 패킷 근거가 있고 지원되는 애플리케이션 프로토콜로 식별됐다. 필드가 없거나 모호하면 자동 차단하지 않는다.
- 승인 계획에는 재검증한 증거의 SHA-256이 포함된다. 원문 페이로드·헤더·비밀 값은 카드에 싣지 않는다.

**초기 WAF 원본 경보와 일반 Wazuh 경보는 자동 선차단 판정 입력으로 지원하지 않는다.** Suricata가 볼 수 없는 HTTPS 본문 공격이나 조건이 부족한 경보는 기존 조사·사전 승인 경로로 처리한다. 2026-10-13 읽기 전용 SSH 조사에서 실제 EVE 경보의 interface·direction·flow 주소·양방향 패킷 필드가 함께 존재함을 확인했지만, 모든 경보가 위 임계조건을 충족한다는 뜻은 아니다.

### 보호 대상

모든 사설·루프백·링크 로컬·예약/비공인·멀티캐스트 주소를 제외한다. 추가로 다음을 보호한다.

- 학교 DGX `.110/.111`이 속한 `211.170.162.0/24`와 지정한 공인 DNS 주소.
- 라이브 `never_block` 셋, 서버의 실제 인터페이스 주소와 기본 게이트웨이, 현재 DNS resolver.
- 활성 SSH 출발지와 활성 외부 서비스 연결의 보호 endpoint.

따라서 **실습 공격 세그먼트 `192.168.16.0/25`도 자동 선차단 대상이 아니다.** 이 대역을 자동 대상으로 넓히거나 예외 `/32`를 임의로 추가하지 않는다. 해당 테스트 호스트 대응은 사전 승인 경로에서 별도로 검토한다.

### 시간과 소유권

| 상태/결정 | 동작 |
|---|---|
| 증거 충족, 기존 차단 없음 | 최대 10분의 절대 만료시각으로 신규 원소 생성 후 유지/해제 카드 요청 |
| 같은 IP 반복 요청 | 같은 요청을 반환하며 만료시각을 연장하지 않음 |
| 카드 게시 실패 | 이번 요청이 소유한 차단을 해제 시도; worker 장애가 있어도 원래 커널 TTL 적용 |
| 관리자 유지 승인 | 정확한 요청을 한 번 소비하여 **결정 시각부터 60분**의 절대 만료시각으로 변경 |
| 관리자 해제 요청 | 다음 처리 가능한 worker에서 해당 요청 소유의 차단만 해제 |
| 무응답·승인 기한 만료·브로커 장애 | 원래 10분 커널 TTL로 자동 해제; 브로커 복구 후 만료 확인·보고만 재시도 |
| 수동 차단이 이미 존재 | 기존 차단을 덮어쓰거나 임시 차단의 소유로 취급하지 않음 |
| 기존 원소의 소유권 표식이 변경됨 | 유지·해제를 거부하며 다른 운영 작업의 차단을 건드리지 않음 |

유지·해제 결정 없이 호출만 반복해서 차단 시간을 늘릴 수 없다. 같은 IP에는 원래 임시 기한 또는 승인된 유지 기한 종료 후 1시간의 cooldown이 적용된다. 동시에 관리하는 활성 요청은 최대 8개다. 무기한 차단은 지원하지 않는다.

원소 comment의 요청 ID·절대 만료시각과 root 전용 상태 파일을 함께 사용한다. 기존 `agent_block`과 만료 reaper의 lock을 공유한다. worker 재시작 후에도 `현재 시각 + 60분`으로 시간을 새로 계산하지 않는다. 재부팅 후 사라진 차단을 무조건 복원하지 않는다.

**처리 지연:** 기존 worker는 룰 변경과 서비스 작업도 수행한다. timer 간격은 10초지만 장시간 설정 검사·재시작·검증 또는 공유 lock 대기 중에는 관리자 해제 결정 처리가 지연될 수 있다. “해제 요청”은 10초 이내 처리 보장이 아니다. 임시 차단의 원래 커널 10분 TTL은 worker 실행과 별개로 만료된다.

**방화벽 재적용 제약:** 현재 NAT/방화벽 로더가 원소 comment를 보존하지 않으면 helper는 소유권을 잃은 것으로 판단해 수정·삭제를 거부한다. 당시 커널에 복원된 TTL에 맡기며, 로더 자체는 이번에 변경하지 않는다. 공통 lock을 따르지 않는 root의 직접 방화벽 변경과의 원자적 배타성까지 보장하지는 않는다. 상태 조회의 `status`는 영속 처리 상태다. 별도로 읽은 `live_block_state`의 `owned`/`absent`/`foreign`/`unavailable`과 실제 관찰시각을 함께 반환한다. 예를 들어 기록상 `kept`여도 재부팅·수동 해제로 실제 원소가 없으면 `live_block_state=absent`이며, 차단이 유지 중이라고 보고하면 안 된다. 관찰 실패를 차단 성공으로 해석하지 않는다.
