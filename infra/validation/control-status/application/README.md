# 관리 상태 후보의 정확 적용·복구 검토

**준비·격리 검증 완료, 운영 적용 승인 대기.** 정본과 현재 설치 파일은 query1.19.137이다. 기존 로그만으로 현재 gateway 메모리에 로드된 버전까지 입증하지 못했다. 새1.19.141은 패치와 root 전용 준비 폴더에만 있으며 아직 적용하거나 재시작하지 않았다. [검증 원장](validation.json) · [정확 계획과19파일 SHA](plan.json) · [이전 상태 형식 시험](../README.md) · [현재 현황](../../../../STATUS.md).

정확 계획 SHA256은 `fd6e7cb98ddbcbefa2c7517f73dc6f549eedc2aca6fb4cdad3e78f0ba2b501c4`다. 승인 대상은 이 계획에 결속된19개 파일과 정해진 적용·확인·원복 절차다. 운영 경로는 관리자231→A→B를 유지한다.

## 적용·확정·원복 순서

1. 정확 계획/실행기/모듈 SHA, 기존19파일·보호9파일, 컨테이너 ID/이미지/마운트, 서비스와 큐를 다시 대조한다. 차이가 나면 적용하지 않는다.
2. **15분 독립 원복 타이머를 먼저 설정**한다. 자동 조사 타이머를 잠시 멈추고 진행 작업이 끝났는지 확인한다. 큐2개와 Native turn writer 잠금 안에서 유휴를 확인하며, 바쁘면 적용을 미룬다.
3. 두 채팅 서비스와 기존 Hermes 컨테이너를 잠시 중지한 후19파일만 원자 교체한다. 컨테이너 재생성·이미지 교체·초기 설치기 실행은 하지 않는다. 중지 중 두 봇 답변과 LLM 자동 조사가 잠시 영향을 받는다.
4. 다시 시작한 두 채팅 프로세스와 heartbeat, Native gateway의 PID·시작 ticks·연결·worker, query1.19.141 시작 관측의 소스 SHA를 대조한다. DB4개의 읽기 전용 quick_check와 보호 설정을 확인한다.
5. 새 실제 채팅/MCP에서 읽기·후속 질문·사건 판단·교차 검토를 확인한다. 성공을 확인한 뒤에만 COMMITTED로 확정해 타이머를 해제한다. 단순 프로세스 active 또는 구조 검사만으로 확정하지 않는다.
6. 시작 확인/파일 대조에 실패하면 원래 소스·영수증으로 돌리고 서비스를 복구한다. 미확정이면 독립 타이머가 같은 원복을 실행한다. **사건·경보·큐 DB는 과거 스냅샷으로 덮어쓰지 않는다.** 다른 관리자가 파일/보호 설정을 바꾼 경우에는 덮어쓰기를 거부하므로 별도 조사가 필요할 수 있다.

실제 콜드 적용·재시작·타이머 발동·운영 원복·새 채팅은 아직 미수행이다. 운영 적용 시 짧은 중단이 있으며 확인이 길어져15분 타이머가 발동하면 새 요청도 중단될 수 있다. 원복된 구버전은 새 사건/meta를 보존하지만 새 완료 조건을 강제하지 않는다.
