# 긴 journal 조회의 분할 후보

**전체24시간을6시간 이하 구간으로 결합하고 native 시각 경계를 마이크로초로 유지하는 후보다. 135검사와 실제 제한 환경에서 B/C 반환을 확인했으나 A의24시간 검색은 여전히12초 제한에 걸린다. 운영 적용 준비는 미완료다.** [실제 읽기 검증](../validation/live-reads/README.md) · [후보·결과 원장](../validation/live-reads/validation.json) · [이전 시간예산 적용](journal-query-budget.md).

| 항목 | 후보의 동작 |
|---|---|
| 기간·대상 | 기존 등록 target·KST·최대24시간 요청 그대로. 최신 구간부터 최대4개, native Unix 시각도 마이크로초로 구성·경계 재검사 |
| 근거 결합 | 같은 cursor는 중복 제거, 다른 내용이면 거절. 전체 결과를 시각/기록 해시로 정렬하고 원래 limit만 반환 |
| 조기 종료 | 엄격히 더 최신인 limit+1개 이상의 결과가 있으면 오래된 구간은 반환 tail을 바꿀 수 없어 중단·has_more=true. 전체 건수/보존 인증은 하지 않음 |
| 실패 | 어느 구간이든 읽기 실패·공유20초 초과면 unavailable. 앞선 빈 구간만으로 전체0건을 반환하지 않음 |
| 제한·권한 | 명령12초/전체20초·원래 전체 바이트 예산·응답60KB/50행·정규식/마스킹·고정 unit/peer UID·rate limit 유지 |
| 전달 계약 | 기존 JSON 필드와 validator를 그대로 사용. MCP 도구·인자·권한·패키지·포트 변경 없음 |

[diagnostic_journal.py](diagnostic_journal.py)의 알고리즘만 바꿨다. 기존 [단일 설치기](../../deploy.sh)→[진단 설치 경로](../../deployment/soc_diagnostics.py)의 고정 source 목록이 같은 파일을 복사하며 설정 예제/오프라인 의존 목록 추가는 없다. 기존 운영에는 전체 설치기를 다시 돌리지 않는다. 신규 OS 전체 설치는 이번에 시험하지 않았다.

## 검증

현재 후보의 [A/B/C 제한 환경·경계 반례](../validation/journal-reader/README.md)를 먼저 따른다. 아래는 초기 e172 후보/134검사의 과거 관측이며 현재 후보의 전 호스트 성공을 뜻하지 않는다.

| 근거 | 결과·한계 |
|---|---|
| 실제 운영 MCP | 현재 모듈의 B rule-worker24시간 journal 실패, root reader 감사 command_timeout. 권한 거부·서비스 중단 아님 |
| 원형 재현 | 고정 severity err 약0.06초, warning/info의 고정 grep12초 초과. 역순24시간도 초과 |
| 개별 분할 | 같은24시간의6시간4구간 모두 반환, 합계13.004초. 각 구간은 오류 후보 표본0건·보존/전체 오류 부재 보장 아님 |
| 통합 후보 | 같은24시간12.638초·기존 validator 통과. root 관리자 격리 함수/실제 journal이며 운영 reader sandbox·MCP 설치/새 채팅 검증은 아님 |
| 회귀 | journal32·진단43·이력24·호스트 인벤토리15·설치20, 총134검사 통과/생략0. 전체 기간·경계 중복/충돌·1µs 범위·상위 tail·all priority·공유 마감·누적 바이트 반례 포함 |

시간은 각1회·디스크 캐시/부하 비통제이며 모델/채팅 지연 개선값으로 뺄셈하거나 일반화하지 않는다. 처음 추가 경계 시험의 중복 keyword 인자 오류는 fixture에서 고쳤고 실패 원문을 보존했다. production 코드를 그 오류에 맞춰 완화하지 않았다.

## 현재 후보와 남은 검증

현재 후보 SHA는 `8f6cdafdb3829ba6c43648a99829f2bee3f28da8190ff1166574025ecca2054c`다. 초기 e172 후보를 보완하여 native `--since=@초.마이크로초`·`--until=@초.마이크로초`를 사용한다. 초 단위로 넓힌 검색에서는 종료 직후의 로그100개가 bounded tail을 채워 필요한2개가 밀리는 반례를 재현했다. 수정 후 journal33/진단43/이력24/인벤토리15/설치20,135통과·생략0이다. 응답의 마이크로초 재검사·중복/충돌·모든 기존 제한을 유지한다.

최신 후보를 기존 reader의 보안/자원 제한과 같은 별도 unit에서 실행했다. A24시간12.123초 실패·B13.500초/C0.305초 반환, A의 기존 로그1µs구간1건 반환0.097초/기존 validator 통과다. 실제 MCP/모델·채팅/운영 적용은0이며 각1회·부하/캐시 비통제다. [정확 결과·시험 오류·채택하지 않은 실험·정리](../validation/journal-reader/README.md)를 보존한다.

A/B/C 설치 소스는 모두 기존 `8336e073a249f9a31d4ea5fd90d506f126aada2bf93ec0dcfa47fc135383c1cc`다. A/C 초기 영수증과 B prepared/증분 영수증을 대조했고 초기 이력을 소급 수정하지 않았다. 운영3소스/unit/reader PID·시작ticks 불변/모두active를 확인하고 자체 격리59파일/15폴더만 제거했다. 기존19파일 상태 후보와 계획은 변경하지 않았다.

[후속 비용·공식API 실험](../validation/journal-native/README.md)에서2동시 읽기로 같은24시간11.946초를 확인했다. 요약 프로토타입으로 표준응답·파일 실패·byte/마스킹·고용량/취소와 A/B/C의 검증이 남았으며 이8f6c 코드의 운영 개선을 뜻하지 않는다. 공통 native 어댑터 구현/회귀·단일 설치 경로까지 확인한 뒤 정확 적용/원복 목록을 준비한다. 승인 전 서버 소스·timer·reader 서비스를 바꾸지 않으며 새 적용 stage/타이머는 아직 없다. 승인 후 원본/메타데이터 백업·독립 원복·해당 reader 재시작·기존 비특권 MCP의24시간 실조회·봇 새 채팅·확정을 구분한다. 실패 시 해당 소스·필요한 reader 상태만 복구하고 journal/사건 DB를 과거 스냅샷으로 되돌리지 않는다.
