## 공통 변경

- Native 실행기의 기존 literal 정정에만 유한 상태 선택을 연결했다. 이미 유효한 현재 모델 판단과 실제 성공 인용이 있어야 하며,새 판단·원인·근거를 코드가 만들지 않는다.
- root가 정한 모드/완료 요건·현재 turn·모델/기존 경로·필수 조회 완료·실제 dispatcher 원장과 완료 이벤트의 원문 SHA가 맞아야 한다. 계산만 수행,조회 실패/누락,원문 변형,이전 turn·다른 모델/경로,중단은 거절한다. 기존 `bind_service_read_attempts`를 재사용한다.
- 모델은 nonce·more_evidence·status만 응답한다. 미해결 판단에서는 resolved를 고를 수 없다. 상태 선택 시 상태 제어 줄만 교체하고 나머지 바이트를 보존한다. more_evidence=true이면 기존 Native 읽기 복귀·기존 예산을 사용한다. 새 도구·권한·재시도·정상/해결 자동 선택은 없다.
- 안내는 기존 soc-investigate의 한 절로 관리하고 workflow_contract로 해당 단계에서만 로딩한다. 평소 조회·조사 프롬프트에는 추가하지 않는다. SDK 봇에 동일한 새 상태 decoder를 배포한 것이 아니며 SDK는 상속된 완료 조건과 회귀 범위다.

## 시험 절차에서 정정한 점

첫 비교8 API 시도 중 이전 후보4건이 생성 전에 HTTP500이었다. 원인은 합성 도구 스키마의 `parameters.properties` 누락이다. 이전 후보에는 도구 목록이 전달됐고 새 상태 선택은 목록을 제거하므로 불균형이 발생했다. 원래 응답과 실패는 보존하되 이 비교는 품질 판단에서 제외했다. 추가2시도에서 원형 실패와 `properties={}` 보충 후 성공을 대조했고,**시험 입력만** 고쳐 양군8생성을 다시 확인했다. 총18 API 시도/13개 정상 생성/생성 전 시험 입력 오류5건이며 운영 오류·새 모델 점수로 합산하지 않는다. 첫 more_evidence의 prefix 측정도 후속 메시지 추가 뒤 비교해 무효였으며 새 비교에서는 요청 직전에 측정했다.

초기 설치46검사 중1개는66265바이트 gate에 오래된64KiB assertion을 적용해 실패했다. 실행기는 이미96KiB 상한과64KiB 초과 실행/96KiB 초과 거절 시험을 사용한다. assertion만 이 기존 규칙과 맞췄으며 실행기 상한은 바꾸지 않았다. Mac/B에서46건을 다시 통과했다. 원본 실패와 최초 동결본을 로컬에 보존했다.
