## 2026-10-25 1.6.0 — IDS 대상·계산·KST 저장

명확한 단일 IDS/Suricata 현재 상태 요청의 첫 읽기 스키마는 실제 등록된 `rule-a.get_service_action_target`의 `a:suricata` enum으로 좁힌다. 모델이 호출을 선택하며, 조회 이후에는 조사·승인안 작성 도구를 복구한다. 다른 장비의 관측으로 IDS를 확인했다고 답하면 기존 한 번의 정정 후 미확인으로 처리한다. 혼합 장비·과거 비교·인용·변경 요청은 이 좁힘에서 제외한다.

조회 응답의 `time_display`에는 서버가 계산한 KST 시각과 경과초/일시분초가 들어간다. 명시적 offset이 있는 제공 시각의 산술은 기존 읽기 MCP의 `calculate_time`을 사용한다. 계산은 SOC 상태 관측·사건 판단·승인 근거로 계산하지 않는다. 최종값 누락, 시각 불일치, JSON의 명확한 시간순/사건 간 차이/최신 사건 경과 필드 불일치는 한 번 정정하고 계속 틀리면 실제 계산 근거만 표시한다. 이는 임의 자연어·모든 JSON 필드의 완전한 의미 검증을 뜻하지 않는다.

일반 본문의 UTC 접두·괄호 접미와 명확한 UTC 시각 표 열을 KST로 변환한 뒤 native 최종 답변 저장 경로로 전달한다. 원본 관측·룰 SHA·승인 diff·과거 대화는 유지하고 원문 코드블록은 보존한다. 이미 KST인 코드블록에 중복 환산 설명을 붙이지 않는다. 관리 gate와 플러그인의 공용 근거 소스는 동일 SHA로 검증한다.

운영 반영과 실제 SDK/DB 저장 검증, 중간 모델 실패 및 JSON 단독 형식 한계는 [STATUS](../../../STATUS.md)에 기록한다. 기존35B/선택적 추론을 유지하고 새 패키지는 필요 없다. 아래 버전별 기록은 당시 검증 범위다.

## 2026-10-24 일반 채팅 1.2 보완

운영 반영 상태와 최종 표본은 [STATUS](../../../STATUS.md) 최상단을 따른다. 아래 1.0/1.1의 범위·제외·실측은 당시 기록이다.

확인된 DGX/custom/Qwen 경로에는 호환 `reasoning_effort=medium`을 요청별로 적용한다. 순수 파일 집계의 읽기 후 최종 문장 단계는 기존 `none`으로 수행하고 해시가 확인된 집계 renderer가 수치·ID를 표시한다. 전역 설정은 유지하고 다른 주소·모델·플랫폼에는 이 추론 예외를 적용하지 않는다. 첫 호출도 모델이 생략할 수 있으므로 실제 호출을 검사하며,0호출 재시도는1회이고 끝내 실행하지 않으면 미실행을 알린다. 6,000자보다 긴 모델 응답도0호출 검사를 우회하지 못하며 장문 전체에 정규식을 실행하지 않는다. 일부 파일만 확인된 집계는 같은 한 번의 예산으로 모델에 누락 대상 조회를 요청한다. 여전히 부족하거나 예산이 없으면 미확인으로 표시한다. 잘못 연결된/모호한 transport 결과는 재시도 근거로 쓰지 않는다.

현재 턴의 호출 ID·대상·본문 SHA가 맞는 파일 정의 집계는 일반 ‘현재 적용된 룰’과 순수 표 요청에도 적용한다. 정의/고유 ID 수·ID 목록과 미확인 범위를 표시하며 전체 CRS/ET나 활성 엔진 룰 수로 부르지 않는다. `runtime_load_verified=false`는 개별 적재 미확인이며 비활성의 증거가 아니다. 분석·원인·변경·원문·JSON/CSV는 파일 집계 renderer로 덮어쓰지 않는다. 장비 표 후속은 앞선 사용자 요청의 주제를 이어받는다. 직전 실제 조회의 연결된 도구 결과·SHA가 전부 검증되고 현재/최신 재조회 요구가 없으면 그 근거를 표로 재정리하며 **앞선 조회 기준·새 조회 없음**을 명시한다. 이 형식 단계는 도구 없음/추론none이고 일부 근거가 부족하거나 최신 요청이면 다시 조회한다. 과거 봇 답변·인용·붙인 JSON을 도구 근거·승인으로 사용하지 않는다.

기존6개 native SHA는 유지하며 `turn_api_request.build_api_request`와 loop alias, 기존 최종 함수2alias를 함께 등록·해제한다. 첫 API의 읽기 유도는 불필요한 무근거 최종 응답/재시도를 줄이기 위한 것이며, 속도/SLA나 일반 답변 정확성 보장은 아니다. 한국어 출력 가드·비검증 중간/추론 비표시와 승인 경계는 유지한다. 새 패키지·이미지·포트가 없어 오프라인 반입 목록의 추가 바이너리는 없다. 기존 단일 설치기는 같은2파일과 동적 소스 SHA를 포함한다.

## 작동 범위

다음 조건을 만족하는 현재 턴을 대상으로 한다.

- 플랫폼은 Mattermost이며, 현재 사용자의 한국어 요청이 읽기 조회에 해당한다.
- 현재 사용자 메시지를 실행 이력에서 확인할 수 있고, 그 이후 실제 도구 호출·결과가 없다. 이전 턴의 도구 호출은 이번 조회의 실행 근거로 쓰지 않는다.
- 모델이 일반 텍스트 종료를 반환했고, 조회·확인·점검 등의 진행 약속이 남아 있거나 명시적인 현재 커스텀·로컬 룰 조회에 대해 근거 없는 완료·현재 적용 상태를 주장한다.
- 인터럽트, 별도 검증 대기, 변경 요청 등 제외 조건에 해당하지 않는다. 추가 실행에는 남은 모델 호출 예산도 필요하다.

조건이 맞으면 아직 조회하지 않았다는 안내를 내부 대화에 추가하고 기존 Hermes 루프를 한 번 더 진행시킨다. `chat_completions`의 다음 API 인자 조립 한 번에만, 현재 노출된 도구 가운데 확인된 읽기 도구 집합을 제공하고 `tool_choice=required`를 사용한다. 집합은 알려진 읽기 도구 이름, 유효한 현재 도구 이름, 보완 준비 시점의 읽기 목록과 실제 builder 반환 목록의 교집합이다. 사라진 도구를 다시 삽입하지 않으며, 실제 반환 목록에 읽기 도구가 없으면 `tools=[]`, `tool_choice=none`으로 제한한다. 어떤 도구와 인자를 선택할지는 LLM이 결정한다. 플러그인이 정해 둔 도구를 대신 호출하거나 MCP 권한을 늘리지 않는다. API builder는 해당 호출에서 즉시 원래 참조로 돌아가며, 취소되거나 턴이 달라지면 요청 인자를 바꾸지 않는다.

이 요청 옵션이 Ollama의 도구 실행을 강제한다고 해석하면 안 된다. 2026-10-16 확인한 [Ollama 공식 호환 문서](https://github.com/ollama/ollama/blob/main/docs/api/openai-compatibility.mdx)는 `tools`를 지원하지만 `tool_choice`는 미지원으로 표시한다. 실제 읽기 도구 스키마 8개와 `tool_choice=required`를 전달한 평가에서도 도구 호출 0회·`finish_reason=stop` 응답이 관측됐다. `required` 전달은 실행 성공의 증거가 아니며, 재시도 후 실제 호출 수를 확인하는 다음 검사가 필요하다.

프로젝트에서 확인한 provider `custom`·모델 `qwen3.6:35b`·API 주소 `http://211.170.162.111:11434/v1` 조합에는 보완 재시도 요청 한 번만 모델의 검증된 기본 thinking 동작을 사용한다. 이를 위해 최상위 요청 인자와 `extra_body` 양쪽에서 `think`, `reasoning_effort`, `reasoning`을 제거한다. API 주소는 끝의 `/`를 제외한 값까지 같고 실제 요청의 모델도 일치해야 한다. 전역 reasoning 비활성 설정이나 agent의 지속 설정은 변경하지 않으며 다음 요청부터 원래 builder의 비활성 설정을 사용한다. 다른 provider·모델·주소는 원래 설정을 보존한다. 모델 기본값에 의존하는 이 선택은 조회 회복을 위한 제한된 방식이며, 추가 추론·재시도로 지연이 늘 수 있다.

이전의 `extra_body.think=true`만 추가하는 시험은 활성화에 실패했다. 실제 요청에 `reasoning_effort=none`이 남아 있었고, [Ollama v0.40.4의 OpenAI 호환 변환 코드](https://github.com/ollama/ollama/blob/v0.40.4/openai/openai.go)는 `reasoning.effort`를 우선하고 없으면 `reasoning_effort`를 사용한다. 따라서 단독 `think=true`를 동작 보장으로 설명하지 않는다. 이전 실패는 검증 JSON에 보존하며, 현재 구현은 위의 상충 옵션 제거 방식이다.

보완 기회 뒤에도 현재 턴의 실제 도구 호출이 없다면, “확인했습니다”처럼 완료를 주장하는 답변도 실행 근거로 인정하지 않고 조회 미실행 안내로 끝낸다. 보완 준비 시 사용 가능한 읽기 도구·유효 도구 목록·API builder·실행 여유가 없거나 지원하는 API 모드가 아니면 재시도 없이 미실행을 알린다. 무제한 재시도나 백그라운드 조회를 예약하지 않는다.

재시도 후 0회 호출이면 조회 미실행 안내로 끝내는 `FALLBACK` 검사가 최종 확인 단계다. 조회 성공을 보장하는 대신 실행하지 않은 상태를 진행 중·완료로 숨기지 않는 범위다.

조회가 실행됐다는 사실과 결과 요약이 정확하다는 사실은 별개다. 배포한 1단계는 규칙 개수·ID 계산이나 모델 판단을 검증하지 않는다. 아래 2단계는 대상 파일의 개수·ID 표시에 한정해 보완하며, 사건 판단의 정확성·응답 속도·일정 시간 내 완료를 보장하지 않는다.

초기 native 검증 두 차례는 실제 읽기 집계가 정확했지만 native의 외부 자료 보호 포장을 JSON으로 바로 읽으려 해 모두 미확인으로 표시되는 실패가 있었다. 이를 성공으로 덮어쓰지 않고 검증 이력에 남긴다. 아래의 정확한 포장 형식 검사 후 최종 검증이 통과했다. 이번 결과는 지정 파일 집계 표시의 범위이며 일반 분석 정확도나 실제 사용자 채팅 전달까지 입증하지 않는다.

단순한 현재 커스텀·로컬 룰의 확인·목록·개수 요청에서는 읽기 도구가 반환한 `rule_inventory`를 사용해 정의 수, 고유 ID와 ID 목록을 표시한다. 집계는 [승인 실행기의 읽기 경로](../../mcp/rule_change_executor.py)가 대상 파일 바이트를 구문 분석해 만든다. 렌더러가 도구를 호출하거나 LLM의 도구 선택을 대신하지 않는다. 대상은 기존의 `a:modsecurity-custom`, `a:suricata-local`, `b:wazuh-local-rules` 세 파일이다.

표시에 사용하는 근거는 현재 사용자 턴 이후의 정확한 `get_rule_change_target` 도구 호출 ID와 결과가 연결되어야 한다. 도구 서버·대상, 집계 버전·범위·자료형, 결과 본문 SHA-256과 집계가 참조한 SHA-256이 모두 맞아야 한다. 과거 턴, 사용자·인용문 안의 도구 모양 JSON, 연결되지 않은 결과, 중복 호출·결과와 새 조회 이후의 오래된 성공은 근거로 사용하지 않는다. 새 조회가 실패하거나 미완료면 이전 성공으로 채우지 않는다.

실제 native 도구 결과에 붙는 `<untrusted_tool_result>` 보호 포장은 호출한 도구 이름과 확인한 고정 문구·개행·끝 표식이 정확히 맞는 한 겹만 해석한다. 임의의 앞뒤 텍스트를 잘라내거나 중첩 포장을 반복해서 벗기지 않는다. 다른 도구 이름, 형식 변경, 사용자 인용문은 집계 근거가 아니다. native가 본문 안의 delimiter를 무해화해 원본 바이트가 바뀌면 SHA 검사가 실패하며, 이를 역변환해 원본이라고 주장하지 않는다. 확인한 형식의 출처는 `agent/tool_dispatch_helpers.py`의 SHA-256 `21a067da35986a1a0fe8f71d553c66d9a344f25b7fcac7f0a016a7ccbceff7a0`이다. 이 자료 형식 검증은 아래 여섯 native hook 파일 핀과 구분한다.

집계 결과가 없거나 지원하지 않는 구문이면 해당 대상은 “집계 확인 불가”로 표시하며 0개로 해석하지 않는다. 모든 요청 대상이 미확인이면 완료했다고 쓰지 않는다. 명시적으로 빈 파일을 성공적으로 분석한 경우에만 0개로 표시한다. 중복 ID가 있으면 정의 수와 고유 ID 수를 나누고 중복도 드러낸다.

로컬 실제 파일 fixture 대조값은 WAF **10개 ID**(12개 `SecRule` 중 체인 조건 2개는 별도 ID가 아님), Suricata **14개**(로컬 SID 12개와 ET 재정의 2개, noalert 표식 1개 포함), Wazuh **19개**(level 0 규칙 1개 포함)다. 주석 속 예약 ID와 비연속 ID 사이의 빈 번호는 포함하지 않는다. 이 값은 로컬 fixture 검증이며 라이브 파일의 최신 상태를 대신하지 않는다.

표시 범위는 **지정한 파일의 규칙 정의**다. 다른 룰 파일, 엔진 메모리에 개별 규칙이 적재됐는지, 차단 모드와 실제 탐지 성공은 집계에 포함하지 않는다. 분석·원인·위험·설명·원문·전체 파일·변경·과거 자료·제공된 내용 검토, 서비스·상태·로그·경보가 섞인 요청이나 표/JSON/CSV 같은 명시적 출력 형식 요청은 모델의 원래 응답 경로를 유지한다. 순수 집계 요청에서 알려진 다른 읽기 도구를 함께 호출한 경우에는 검증된 파일 집계를 유지하고 그 도구의 숫자를 집계 근거로 사용하지 않는다. 대상 파일 읽기를 하지 않았거나 잘못된 인자로 호출했다면 미확인으로 표시한다. 알 수 없는 도구나 보호된 작업이 섞인 턴은 집계 응답으로 대체하지 않는다.

검증된 목록은 기존 native 최종 응답 함수에 전달한다. 사용자에게 반환하는 본문과 저장하는 본문이 같고 이전 reasoning·provider sidecar와 잘린 응답 조각이 다시 섞이지 않도록 한다. 기존 대화 DB를 재작성하거나 승인 정책·도구 권한을 바꾸지 않는다. 자세한 경계는 [집계 렌더링 회귀](./test_inventory_render.py)와 [실행기 집계 회귀](../../mcp/test_rule_inventory.py)에서 확인한다. 이 제한된 렌더링 밖의 모델 응답 정확도는 별도 검증 대상이다.

## 문맥과 권한 경계

Mattermost 스레드 문맥이 붙은 요청은 [문맥 플러그인](../mattermost-context/README.md)의 검토된 JSON 형식에서 현재 사용자 요청만 분리한다. 과거 댓글·자동 보고의 인용문을 현재 요청, 승인 또는 실행 지시로 취급하지 않는다. 알 수 없는 문맥 형식은 임의로 해석하지 않는다.

초기 감지는 한국어 표현과 제한된 길이·형식에 대한 좁은 검사다. 현재 커스텀·로컬 룰의 근거 없는 완료 주장 검사는 명시적인 조회·확인·목록 요청에 한정하며 개념·정의·작성법, 과거 결과의 요약, 첨부·제공된 내용 분석은 제외한다. 인용·코드 예시, 번역 요청, 정직한 실패 안내, 질문과 승인 대기도 구분하며, 모든 우회 표현과 다른 언어를 포괄하는 범용 판정기는 아니다. 이미 도구를 호출한 턴의 오류나 도구 결과 이후 모델 정지·채팅 전송 실패는 별도 조사 대상이다. 재시도 후 완료 주장까지 제한하는 처리는 이 플러그인이 보완을 시작한 해당 턴에 적용하며, 모든 답변을 전역적으로 바꾸지 않는다.

일반 sudo·Docker 실행, 패키지 설치, 컨테이너 재구성, 규칙 쓰기 권한을 추가하지 않는다. 기존 쓰기 MCP의 정확 후보 승인과 제한된 worker 실행 경계는 그대로다. 내부 보완 안내나 `tool_choice=required`는 관리자 승인으로 사용할 수 없다.

## 소스 고정과 시작 확인

공개 완료 훅 API 대신 검토한 native 실행 경로의 런타임 참조를 감싸는 구현이다. [플러그인 소스](./__init__.py)의 `SOURCE_SHA256`에 다음 일곱 파일을 고정하며, 다른 바이트면 등록을 거절한다.

- `agent/turn_final_response.py`
- `agent/conversation_loop.py`
- `agent/turn_context.py`
- `agent/message_metadata.py`
- `agent/turn_api_request.py`
- `agent/chat_completion_helpers.py`
- `agent/turn_api_call.py`

Hermes 원본 파일을 덮어쓰지 않는다. 등록 과정은 원래 함수 참조의 일치와 기존 wrapper 충돌을 검사하고 `on_unload`에 모듈 함수 참조를 원복하는 처리를 등록한다. 다만 hot unload 시 이미 agent 인스턴스에 예약된 1회 API 요청 builder는 다음 호출까지 남을 수 있다. 모듈 참조 원복과 모든 실행 중 인스턴스의 즉시 해제는 다르므로, 운영 해제에는 아래의 동일 컨테이너 재시작 절차를 사용한다. 별도 한국어 출력 가드가 관리하는 `plugins/platforms/mattermost/adapter.py`, `gateway/run_turn.py`의 두 파일 핀은 다른 계약이며 유지한다.

실제 시작 뒤에는 해당 프로세스의 `capstone.query_completion` 로그에서 버전과 `aliases_installed=True`를 확인해야 한다. 설정의 enabled 목록이나 플러그인 파일 배치만으로 성공을 판단하지 않는다. 등록 로그는 해당 프로세스에 보완 함수가 연결됐다는 근거이며, 실제 조회 완료·답변 정확도·Mattermost 전달까지 확인한 결과는 아니다. Hermes 버전이나 내부 소스가 바뀌면 새 소스·API 계약·회귀 시험을 검토한 후 핀을 갱신한다. 등록 거절을 해결하려고 검사를 제거하지 않는다.

## 배치와 초기 설치

`plugin.yaml`, `__init__.py`, `alignment.py`와 [공유 소스4개](../chat-harness.md)를 `$HERMES_HOME/plugins/groot-query-completion/`에 두고 `config.yaml`의 `plugins.enabled`에 `groot-query-completion`을 추가한다. 이 환경의 컨테이너 안 `HERMES_HOME`은 `/opt/data`이며, SSH용 HOME인 `/opt/data/home`과 구분한다.

플러그인과 설정은 영속 데이터에 있으므로 동일 데이터를 마운트한 기존 컨테이너의 재시작에도 유지된다. 컨테이너를 재생성할 때도 해당 데이터와 호환되는 검토 이미지를 함께 보존해야 한다. 데이터가 없는 새 컨테이너나 새 이미지 자체에 자동 포함되는 구성은 아니다.

[초기 SIEM 설치기](../../../deployment/roles/siem.sh)는 기존 Mattermost 확장 5개 파일에 새 플러그인 2개를 더해 복사하고 활성화한다. 새 파일도 배포 프로필의 소스 SHA에 포함되며, 준비 이미지의 여섯 native 파일과 unload API를 서비스 생성 전에 검사한다. 기존 읽기 MCP 2개·읽기 전용 초기 정책은 유지한다. 2단계 집계는 `rule_a/rule_b`의 대상 파일 읽기 도구가 이미 노출된 구성에서만 사용할 수 있으며, 기본 SIEM 단계는 그 도구나 쓰기 MCP를 추가하지 않는다. 후속 SOC 확장 단계에서 승인형 MCP를 연결하므로 초기 설치 전체 범위와 구분한다. 초기 설치 범위와 새 VM 검증 한계는 [배포 안내](../../../deployment/README.md)를 따른다.

## 복구

운영자가 현재 대화와 관리 작업의 idle 상태를 확인하고 기존 자동 실행 제어 절차를 따른 뒤, 현재 config를 보관한다. `plugins.enabled`에서 `groot-query-completion`만 제외하고 같은 Hermes 컨테이너를 재시작한다. 다른 플러그인·모델·MCP·자격 설정은 보존한다. 시작 상태와 기존 읽기 경로가 회복됐는지 확인하고 원래 활성화되어 있던 timer를 복구한다.

이 플러그인을 끄기 위해 이전 대화 DB를 복원하지 않는다. 오래된 DB 복원은 이후 대화를 잃을 수 있다. 새 정책 문구와 플러그인 활성화는 구분해서 관리하며, 프로세스 재시작으로 런타임 보완을 해제한다. 복구 성공은 실제 시작·상태 확인 결과로 기록한다.

## 검증 결과와 남은 확인

검증 근거 JSON에서 배포 전 평가와 배포 후 상태 확인을 구분한다. 현재 범위는 다음과 같다.

- 합성 대화와 native 계약 시험: 현재 턴 구분, JSON 문맥 분리, 읽기 도구 제한, 한 차례 보완, 호출 없는 완료 주장 처리, 예산·인터럽트·승인 경계, 소스 불일치 거절과 unload 원복.
- 2단계 로컬 회귀: 집계 렌더링 65개, 실행기 집계 28개, 기존 조회 보완 85개와 초기 SIEM 설치기 36개가 통과했다. 실제 파일의 정확한 ID·개수, 주석·체인·level 0·noalert 구분, 현재 턴·호출 ID·SHA 연결, native 보호 포장, 부분 실패·중복·과거·인용 자료 배제, 명시적 원문·분석·출력 형식 보존과 native 저장 본문 일치를 확인했다. 로컬 결과는 서버 배포 확인과 실제 사용자 채팅 시험을 대신하지 않는다.
- 실제 모델 평가: 1단계 시험은 읽기·최종 답변을 회복했지만 집계·상태 서술 오류가 남았다. 2단계 최종 실제 모델 평가는 57.38초·API 3회·읽기 3건으로 정확한 10/14/19개와 ID 목록, 반환·저장 본문 일치를 확인했다. 별도 합성 응답 시험은 12.046초·native 반복 2회·실제 읽기 3건으로 잘못된 999개 주장 대체를 확인했다. 초기 보호 포장 미인식 실패 2회도 이력에 보존한다.
- 배포 후 상태 확인: 2단계 `1.1.0`의 같은 컨테이너 시작 이후 등록 로그, native 파일 핀 유지, Mattermost/API 연결·새 heartbeat·timer·설정·DB 보존을 21:02:22 KST 확인했다. Docker 로그만 확인했던 초기 검사의 실패는 별도 기록했다.
- 외부 영향 확인: 실제 Mattermost POST·규칙 변경·보호된 작업 실행과 모델 호출 수는 검증 JSON의 해당 항목으로 구분한다. 실제 사용자 채팅의 전달·화면 표시 시험을 위 native 평가나 등록 확인으로 대신하지 않는다.

문제 이력 재현의 입력도 별도로 대조했다. 해당 세션의 DB 역할별 레코드는 `user=4`, `assistant=3`, `session_meta=1`이었고 도구 레코드는 없었다. 이 재현에서 도구 이력이 보이지 않는 이유는 평가 코드의 역할 필터가 실제 도구 이력을 누락했기 때문이 아니다. 이 사실은 재현 입력의 범위를 설명할 뿐, 보완 이후의 도구 호출 성공이나 답변 정확도를 입증하지 않는다.

같은 실제 모델·문제 이력·native 실행 경로에서 thinking을 활성화한 비교 평가는 49.444초가 걸렸고, WAF·Suricata·Wazuh 읽기 조회 3건과 최종 답변이 완료됐다. 실행 회복은 확인했지만, 최종 답변의 표 사용과 DetectionOnly 차단 효과·규칙 ID 범위 과장 때문에 답변 정확도는 실패로 판정했다. 이는 한 표본의 결과이며 일정 시간 내 완료나 정확도 향상을 보장하지 않는다. 이 비교 평가와, 재시도 한 요청에서 상충 옵션을 제거해 모델 기본 thinking을 사용하는 최종 플러그인의 시험·실제 배포는 별도 검증 단계로 기록한다.
