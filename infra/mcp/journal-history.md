# 사건 당시 서비스 오류 조회

2026-11-06. 복합 조사에서 과거 사건을 묻는데 최근4시간 스냅샷만 조회하던 공백을 보완했다. 기존 `get_system_diagnostics`에 KST 양끝 시각을 추가했다. 새 도구·서비스·포트·키·패키지·일반 셸/sudo 권한은 없다. 최종 보고30초 달성과는 별도이며 [실측 원장](journal-history.validation.json)과 [현재 상태](../../STATUS.md)를 따른다.

## 사용과 한계

```json
{"target":"c:apache","since_kst":"2026-11-05T19:10:00+09:00","until_kst":"2026-11-05T20:00:00+09:00","limit":20}
```

- 양끝은 초와 `+09:00`을 포함하고 함께 지정한다. 미래 시각은 거절하며 최근30일 안의 최대24시간을 검색한다. `lookback_minutes`와 혼용하지 않는다.
- 기존 등록 systemd25대상만 이력을 제공한다. `*:systemd`, runtime 및 `soc:coverage`는 현재 상태용이다. 시각을 생략한 기존 조회 계약은 유지한다.
- root가 분류한 오류 메타데이터를 시간·unit으로 **먼저 검색한 뒤** 최대50건을 반환한다. 원문 journal, MESSAGE, 커서, 환경, 명령, HTTP 본문은 반환하지 않는다. 커서는 SHA256으로 중복을 식별하고 마이크로초 시각을 보존한다.
- `kind=journal_history`에는 현재 서비스 `properties`가 없다. `indexed_error_count`는 이 제한된 색인의 일치 수, `returned_error_count`는 반환 표본 수다. 전체 journal 건수는 `null`이다.
- `history_coverage.status=scanned_sample`은 고정 필터로 해당 구간을 읽었다는 뜻이다. 원본 로그 보존의 완전성·침해 부재·정상·복구 증명이 아니다. `partial_or_unavailable`, `publisher_stale`, `has_more`를 함께 읽는다. 0건을 정상으로 바꾸지 않는다.

## 수집·보관·권한

기존60초 collector가 이미 실행하는 두 journal 조회 결과를 재사용한다. 매 주기의 journal 호출 수를 늘리지 않는다. 고정 필터는 우선순위0~3, 그리고 우선순위4~6 중 검토된 오류 분류이며 각 조회8초/1MiB/1,001행 상한이다. 수집 실패 구간은 성공한0건으로 발행하지 않는다.

최초 설치에서만 root가24시간을4시간씩6구간으로 수집한다. 전체일 단일 조회는 실제 B에서8초 제한을 넘겼다. 분할 후 B는26.99초/232개, C는8.36초/1개 메타데이터를 읽었다. A는48.10초/6구간 중3개 실패로 일부 공백이 남았다. 이 시간은 **초기 준비 시간**이며 사용자 MCP 호출마다 journal을 재검색하지 않는다.

색인은 `/var/lib/capstone-diagnostics/journal-history.sqlite3`에 root:`capstone-diagnostics` 0640으로 보관한다. 최근30일·100,000행·32MiB 상한이며 초과 시 오래된 정제 메타데이터의 보관 경계를 명시한다. 원본 journal의 회전·보존·삭제 정책은 변경하지 않는다. 저장 실패는 오래된 수집본/조회 불가로 드러나며 정상 판정으로 대체하지 않는다.

A/C의 기존 강제 SSH reader는 EOF 입력이면 예전 snapshot, 최대4KiB JSON이면 제한된 과거 조회를 수행한다. 원격 명령/임의 경로/unit/SQL/셸은 받지 않는다. B MCP의 같은 권한과 고정 경로를 사용한다. SQLite 읽기는 읽기 전용 URI와 한 트랜잭션으로 count/행/범위의 일관성을 유지한다.

초기 진입점 `deploy.sh`와 `deployment/soc_diagnostics.py`가 새 라이브러리 복사·24시간 초기 수집·소스 영수증을 연결한다. 기존 `soc_monitoring.py`의 소스 동기화에도 포함했다. Python 표준 라이브러리 SQLite만 사용하므로 deb/wheel/image 추가 반입은 없다. 초기 설치기를 기존 운영 서버에 재실행하지 않는다.

복구본은 각 서버 `/var/lib/capstone-journal-history/20261106-v2/{a,b,c}/deployment`에 보존한다. 원복은 기록된 소스·권한을 복원하고 진단 timer를 확인하는 작업이다. 운영 DB·승인·채팅·원문 journal을 삭제하지 않는다. 확정된 자동 원복 스크립트는 no-op이며 수동 전체 원복 실행 시험과 구분한다.

## 복합 보고 재시험

이전 약214초 시간초과와 같은 개발 사건·같은 요청을 새 세션/별도DB에서 실제 모델과 Native MCP로 재시험했다. **88.149초에 실패 보고**로 끝났으며 성공한 조사나 속도 개선으로 집계하지 않는다.17시도 중15실제 MCP 성공/2회 실행 전 거절·쓰기0이었다. 모델이 새 과거 조회를 사용했지만 명시된 c:apache 대신 c:sudo-status를 선택했고, 이미 알려진 operation ID를 rule-change getter로 두 번 선택했다. 운영 사건/승인/채팅을 변경하지 않았다.

도구의 과거 조회 공백은 보완했으나 잘못된 대상·ID 선택과 반복 조회를 더 줄여야 한다. 같은 개발 사건이며 공유GPU 부하/실시간 관측 시각을 통제한 독립 성능 비교가 아니다. 최종30초·전체 채팅 왕복·보고 정확성은 미완료다.

최종10:52~10:53 운영 소스·timer·색인 무결성/WS/worker를 확인했다. A의 현재 journal도 unavailable이어서 동일 시각/구간으로 **원본 소스8.415초와 새 소스8.398초를 별도 실행해 둘 다 동일 실패**를 확인했다. 새 이력 기능으로 생긴 회귀라고 단정하지 않으며 A 원본 수집 시간 초과는 남은 과제다. 운영 snapshot/원문/복구본/검사 DB·trace를 보존하고 이번 서버 반입 소스29개와 Mac 자체 임시18개는 SHA 감사 후 삭제·부재 확인했다. 새 패키지0.

실제 trace에서 모델 선택12회 호출의 공급자 시간 합계는68.856초, 도구 결과17건의 duration 합계는6.442초(실행 전 거절2회 포함)였다. 각 단계의 합계이며 전체 채팅 왕복 평균으로 해석하지 않는다. 이 표본에서는 반복된 모델 선택 비용이 더 크다.
