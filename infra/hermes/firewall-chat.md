## 실채팅에서 발견한 문제

독립 세션의 성공 뒤 실제 새 스레드에서 INPUT 조회→표 재정리→`output만`을 시험했다. Ollama는 마지막 요청에서 모델1회·MCP0회로 임의 관측 시각과12개 규칙을 작성했다. Hermes는 표 재정리에 불필요한 MCP1회를 사용했고, OUTPUT 답변도 실제 전체 hook 범위와 다른1체인18개를 작성했다. 이전 단일 inet/output의 실제 정의14개와 전체 OUTPUT hook/참조 범위5체인19개를 구분해야 한다. 이전 실패 원문/DB는 지우지 않고 같은 스레드에 재조회·정정 요청을 추가해 최신5/19를 확인했다.

원인은 직전 사용자 문장만 전달해 재정리 다음의 짧은 범위 변경에서 대상을 잃던 경로, 첫 root 요청과 후속 요청의 근거를 연결할 메타데이터가 없던 경로다. 이를 모델 추가 학습으로 고쳤다고 표시하지 않는다.

| 보완 | 경계 |
|---|---|
| 최근 같은 사용자 연속12요청의 조회 대상/필터만 연결 | 다른 주제·쓰기·승인·잘린 이력을 넘어 과거 대상을 찾지 않음 |
| 대상 없는 새 root의 `output만` | 장비를 한 번 확인하며 모델/MCP를 실행하지 않음 |
| Native root/요청/채널/요청자 좌표 | 실제 Mattermost API에서 검증한 trigger 좌표만 연결. 인용 이력은 여전히 신뢰하지 않는 자료·승인 아님 |
| 새 실제 조회와 순수 표 재정리 구분 | fresh 요청은 새 영수증, 재정리는 같은 대화의 검증된 원문/시각만 재사용 |
| 미조회 수량 확정 방지 | 짧은 hook 요청도 실제 읽기 없이 규칙 수를 확정하지 못하도록 보완 |

## 새 스레드 재시험

두 전용 채널에서 봇별 아래5건을 실제 게시·갱신하고 API 본문과 SDK queue/native session의 호출·원문을 대조했다. 다른 봇의 응답과 보호 호출은0이었다. 확인 질문의 partial은 의도한 대상 확인이며 조회 실패/0건으로 세지 않는다.

| 요청 | Ollama / Hermes 결과 | 실제 MCP |
|---|---|---|
| FW input만 보여줘 | INPUT1체인/14규칙 | 각각1 |
| 각각 표로 보여줘 | 같은 INPUT·원래 관측 시각, 새 조회 없음 | 각각0 |
| output만 | OUTPUT 시작3+참조2체인/19규칙 | 각각1 |
| FW 전체 룰 보여줘 |8테이블/30체인/103규칙 | 각각1 |
| 별도 새 root의 output만 | 대상 확인 질문 | 각각0 |

대응10조건을 모두 확인했다. SDK 표 재정리/확인 질문은 모델0회도 DB에서 확인했다. Native는 연결된 실제 MCP 횟수와 local-format 경로를 확인했으며 내부 API 루프 카운터를 SDK 모델 횟수와 동일 지표로 취급하지 않는다. 양쪽 진행 문구 갱신도 실제 API에서 관측했다. 같은 질문·같은 스레드·같은 메모리로 얻은 결과를 새 대화 독립 시험으로 표시하지 않는다.

서버 SDK191·Native384·context66, 총641검사를 통과했다. 뒤의 빈 줄 수정 뒤 SDK191·Native384를 다시 검사했으며 반복분을 합계에 중복 합산하지 않는다. 초기 설치 소스 묶음/도구 계약2개도 통과했다. 신규 서버 실제 설치와 새 패키지·이미지·키·권한 변경은0이다.

## 표 구문과 남은 분할 문제

실제 게시 본문을 [Mattermost 고정 marked 소스](https://github.com/mattermost/marked/blob/467bc9e99fc75d69424188dfbea7fe0409a9fc15/lib/marked.js)로 검사했다. 파일36,485B·SHA256 `7a7e73ca0aad7145c2c38ff4d02ae431c264221f6fa1771dfa662f125e60789c`, MIT 표시를 확인했고 기존 Node26.8.2만 사용했다. 첫 검사기는 fork의 `{tokens,links}` 반환형을 배열로 오해해 실패했으며 검사기를 수정했다.

공통 FW 상세 표 앞의 빈 줄 누락을 고친 뒤 실제 OUTPUT 정정 응답은 Ollama에서 요약5행·개별16행의 표2개로 해석됐다. 전체19규칙 중 첫 표시 페이지16개이며 나머지3개는 다음 표시 페이지다. Hermes에서는 동일 본문을 여러 메시지로 나누는 과정에서 개별14행만 표,2행은 헤더 없는 텍스트로 전달됐다.16행 자체와 원문19규칙은 보존됐지만 표 표시 완료로 표시하지 않는다. Native `truncate_message`가 코드펜스는 보존하고 표 헤더는 계승하지 않는 사실을 설치 소스에서 확인했다.

다음 보완은 **같은 표시 범위·원문·16행을 보존하면서 Mattermost 분할 경계에 표 헤더를 유지하는 것**이다. 실제 조회량/표시 범위를 줄여 통과시키지 않는다. 브라우저 제어 초기화 실패로 실제 화면은 미확인이고, 파서 성공을 화면 검증으로 대신하지 않는다.

## 운영 반영·복구

관리자231→A→B 경로로 runtime11파일+설치 영수증2개를 SHA/CAS로 증분 반영했다. 최초13:33:22 KST 반영, 빈 줄 추가 수정13:41:35,13:47:38 실제 근거·소스13/보호 설정6 SHA·인증된 두 웹소켓/worker 확인 후 현재 조회 단위를 확정했다. 두 단계에서 소비자/Hermes를 각각 한 번 재시작했고 운영 DB는 되돌리거나 삭제하지 않았다. 모델·FW 정책·승인/보호 주소·TTL은 유지했다.

root `/var/lib/capstone-fw-chat/20261104-r1/deployment`에 원본1.5.17·후보/중간/최종 SHA·권한·manifest·운영자 복구를 보존한다.15분 독립 원복 타이머를 두고 검증 후 해제했다. 중간 후보 SHA도 복구 대상에 포함하고 동시 외부 변경은 덮지 않는다. 확정 recover no-op은 확인했으나 실제 수동 원복은 미실시다.

```bash
python3 -B /var/lib/capstone-fw-chat/20261104-r1/deployment/rollback.py --manual
```

기존 canonical 복사 경로가 같은 소스를 배치하며 초기 설치기는 실행하지 않았다. 임시 시험 소스/파서·다운로드는 정리하고 원문 로그/근거는 로컬 전용으로 보존한다. Git에는 소스·작은 검증 원장·현황만 남긴다. 현재 후보의 성공은 LLM 전 관제 업무·실제 공격 E2E·논문·발표 완료를 뜻하지 않는다.
