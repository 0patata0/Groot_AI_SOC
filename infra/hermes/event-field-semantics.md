# 사건 보고 필드와 판단 근거

2026-10-31. query-completion `1.16.4`, chat-contract `1.5.5`. Hermes와 Ollama 봇은 같은 공통 소스의 설명·검사를 사용한다. 이 변경은 사건 위험도를 코드로 결정하지 않으며 기존 읽기·승인·실행 권한과 모델을 유지한다.

## 필드 해석

- `http_status`는 관측 응답 코드다. 코드만으로 WAF가 차단했는지, 명령 실행이나 침해가 성공·실패했는지 결정하지 않는다. 302는 임시 리다이렉션 응답이며 생성 구성요소와 보안 대응 결과는 별도 근거가 필요하다. [RFC 9110 §15.4.3](https://www.rfc-editor.org/rfc/rfc9110.html#name-302-found).
- `engine`은 해당 경보에 기록된 모드이며 현재 설정 조회가 아니다. `DetectionOnly`에서는 ModSecurity 규칙의 disruptive action을 실행하지 않는다. 이 사실을 다른 구성요소의 차단 부재나 침해 결과로 확대하지 않는다. [ModSecurity 공식 설명](https://github.com/owasp-modsecurity/ModSecurity/wiki/Reference-Manual-%28v3.x%29#secruleengine).
- `transaction_id_sha256`은 원본 식별자의 해시다. 원본 `transaction_id`로 표시하거나 원본 ID를 받는 조회의 인자로 사용하지 않는다. 앞부분만 표시할 때도 해시 축약임을 밝힌다.
- `waf_rule_matches`의 설명은 같은 항목의 센서 `rule_id`와 연결한다. `wazuh_rule_id`는 별도 상관 규칙이다. 현재 경보 MCP는 Wazuh 원문 description을 반환하지 않는다. 필요하면 제공된 `b:wazuh-local-rules` 조회로 현재 정의를 확인하되 과거 사건 당시 적용 여부는 따로 구분한다.

Wazuh description 추가 후보는 기존 원문 제외 회귀 검사에서 거절되어 반영하지 않았다. 센서/상관 규칙을 혼동하지 않기 위해 반환 범위나 원문 비공개 검사를 완화하지 않는다. [기존 조회·표본 계약](../mcp/event-evidence-window.md).

## 공통 검사와 한계

초기 안내·조회 후 판단·실패 정정에 같은 필드 설명을 전달한다. 실제 성공 결과의 SHA를 검증한 뒤 다음 좁은 오류를 검사한다.

1. HTTP 코드 자체를 WAF 차단/리다이렉트 주체 또는 침해 성공/실패의 근거로 쓰는 명시적 인과 표현.
2. 실제 반환 해시 또는 앞부분을 원본 transaction ID로 표시하는 표현.
3. 실제 센서 설명을 같은 경보의 Wazuh 규칙 설명으로 옮겨 붙이는 표현.
4. 경보 조회만 수행했는데 기록된 모드를 현재 설정이라고 명시적으로 단정하는 표현. `현재 ...인지 확인해야 한다`는 조사 계획은 단정이 아니며 실제 초안 재생에서 발견한 오탐을 수정했다.

`security-events`의 `field_semantics`는 엔진 모드의 사건 기록 범위, HTTP 코드와 실제 실행 결과의 차이, 해시/원본 ID, 센서/상관 ID의 구분을 명시한다. 원본 description·본문·헤더를 추가로 노출하지 않는다.

첫 사건 조회를 선택할 때 단일 IPv4 출발지가 명확한 `IP이 DVWA에서`, `IP → DVWA` 표현도 실제 스키마의 `source_ip`로 제한한다. 출발지·목적지가 함께 있거나 CIDR·대상 주소만 있는 경우 단일 출발지로 추정하지 않는다. 모델이 실제 호출과 시각을 고르며 추가 조사 전체에 대한 네트워크 ACL을 만든 것은 아니다.

서로 다른 절의 주장을 구분하므로 뒤에 '침해 성공 미확인'을 붙여도 앞의 '302가 WAF 차단을 시사한다'는 추론이 정당화되지 않는다. 부정·미확인 설명과 별도 근거에 따른 실행 판단은 허용한다. 같은 설명이 실제 두 계층에 모두 제공된 경우는 충돌로 분류하지 않는다.

검사는 완전한 자연어 의미 검증기가 아니다. 표현 변형·다른 근거 혼동이 빠질 수 있으며 통과를 사건 판단 성공으로 세지 않는다. 기존 모델 정정 예산·반복 종료·미완료 보고를 유지하며 임의의 위험 등급이나 '정상' 답을 대신 생성하지 않는다. 실응답은 별도로 수동 대조하고 실패 초안을 보존한다.

## 설치·복구·평가

루트 `deploy.sh`의 기존 SIEM/ollama-trial 소스 경로에서 공통 계약·하네스를 복사한다. 새 패키지·이미지·포트·키·계정·MCP 권한은 추가하지 않았다. 운영 B는 기존 소스 SHA와 유휴 상태를 확인하고 공통 controller 잠금 아래 최종13개 운영/오프라인 파일을 소유권·모드 보존해 교체했다. 두 채팅 프로세스만 재시작했고 Thor·보안 엔진은 변경하지 않았다.

복구본은 B의 `/var/backups/capstone-evidence-semantics-20261031-043436`, `...-044130`, `...-044817`에 보존한다. 단계별11·10·8파일을 교체했고 대상의 합집합은13개다. 전체 변경 이전으로 복구할 때는 진행 중 요청이 없는 때 최신 단계부터 역순으로 manifest의 대상·기존/신규 해시를 대조하고 해당 파일만 복구한다. 이후 변경이 있으면 무조건 덮어쓰지 않는다. 복구 후 두 봇의 시작/연결과 소스 해시를 다시 검증한다.

[검증 원장](event-field-semantics-validation-2026-10-31.json)에 정적/격리 검사와 실제 새 스레드 응답을 구분한다. 과거 개발 사건 재사용은 독립 평가나 실제 공격→승인→차단→복구 E2E가 아니다. 시간은 서버 게시부터 최종 메시지 생성/갱신까지며 클라이언트 표시·푸시 지연을 포함하지 않는다.
