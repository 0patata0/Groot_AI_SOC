# 소스·캐시·소비자 조정 실행기

소스를 바꾸는 동안 수집기와 봇이 서로 다른 계약으로 캐시를 읽지 않도록 실행기를 연결했다. **격리 검증을 마친 후보이며 운영 적용 준비는 미완료다.** 임시 장치 정리·현재 설치 출처·실제 systemd/독립 복구·정확한 전체 payload 승인과 MCP·두 봇 채팅 인수가 남았다. [소스 고정](coordinator-manifest.json) · [검증 원장](coordinator-validation.json) · [현재 상태](../../../STATUS.md).

## 왜 필요한가

B의 읽기 MCP가 Hermes 컨테이너 밖 SSH 세션에서 실행되는 것을 실제로 확인했다. 컨테이너만 멈추면 이전 코드로 시작한 MCP가 남는다. A 감시와 B의 모델·입력 감시도 공통 코드를 읽으므로 함께 정지·대기시켜야 한다. 보안 엔진·로그 수집·스토리지 감시·차단 만료 작업은 정지 목록에 넣지 않았다.

소스만 원복하면 새 정책이 쓴 캐시 표식이 남을 수 있다. 반대로 복구를 반복해 이미 재개한 기존 수집기의 새 관측을 덮으면 기록이 사라진다. 실행기는 소스와 캐시 복구 완료를 각각 영속 기록한 뒤 수집을 재개하고 이후 재시도에서는 캐시를 다시 덮지 않는다.

## 공통 계약과 고정 범위

| 구성 | 하는 일 | 경계 |
|---|---|---|
| 파일·reader·MCP 중계 | A7/B36/C7 합50경로·전후 SHA/소유자/권한·불변 백업·단계별 조회/재접속 차단 | 기존 shell launcher 보존·알려지지 않은 파일 덮어쓰기 불허 |
| 상태·보관·계획 | 호스트 잠금·단계/nonce·정확 plan/bundle·기계/계정/CID/보호 설정 결속 | 18보조 파일·39제어 문서·임의 경로/명령 불허 |
| 서비스·보조 unit·프로세스 | 고정 timer/service·정확 CID만 제어, 전용 읽기 계정의 SSH 자식만 pidfd로 종료·재확인 | 일반 SSH·보안 엔진·다른 계정은 대상 밖 |
| 캐시·원자 생성 | 고정 메타데이터 DB·원본/새 관측 보존·덮어쓰기 없는 원자 생성 | 사건/대화/승인 DB·원시 journal 복구 아님 |
| 조정·운영자 진입점 | 준비·정지·백업·적용·검증·소스 확정·재개·원복 연결 | root 전용 고정 경로·모델/MCP 도구 아님 |
| 재현·구조 검사 | 고정 소스14프로필·공식 Harness² 재검사 | 실제 서비스/MCP/봇 품질과 구분 |

Mac에는 패키지를 설치하지 않았다. A/B의 상태 읽기는 기존 감시·MCP 인증 경로를 사용하도록 작성했으며 새 키를 만들거나 복사하지 않는다. 관리자 작업은 관리자231 경유를 유지한다. 후보 복구 unit의 고정 root capability는 아직 운영에 설치하거나 LLM에 위임하지 않았다. 이 권한과 서비스 중단 범위도 최종 정확 승인에 포함해야 한다.

## 단계와 복구

| 단계 | 조건과 결과 |
|---|---|
| 준비 | 원본·원래 unit/CID 상태 보관→조회 중계/상태 서비스/독립 복구 장치 준비. 기존 수집/소비자는 아직 정지하지 않음 |
| 차단·정지 | 새 조회/MCP 재접속 차단→소비자 timer 정지→진행 작업 유휴 확인→고정 서비스/CID 정지→수집/기존 읽기 자식 종료 확인 |
| 백업·적용 | 모든 호스트의 기존 소스·기존 캐시·백업 완료 근거가 일치해야 첫 핵심 소스 변경 |
| 검증 | 새 reader/수집 실행 시각·실제 로드 자원 제한·새 캐시 정책 확인. 소비자는 계속 차단 |
| 소스 확정·재개 | A·C 뒤 B를 마지막으로 소스 확정. 새 전역 근거가 일치할 때 원래 활성 서비스만 재개 |
| 확정 전 원복 | 원본 소스·캐시·복구 완료 기록 확인 뒤 기존 수집 재개. 소비자는 전역 일치 전까지 차단 |
| 확정 후 원복 | 독자 원복 불허. 별도 정확 승인·모든 호스트의 새 정지 근거·공통 원복 결정 필요 |

`confirmed`는 소스 확정이며 전체 운영 인수가 아니다. 실제 MCP·두 봇 새 채팅과 의미·누락을 따로 확인한다. 일부 확정·연결 단절 상태에서 물리적인 분산 원자성을 보장하지 않는다. 근거가 없으면 차단 상태를 유지하고 조정을 기다린다.

준비만 하고 중단된 경우 서비스가 멈춘 것으로 가정하지 않는다. 원복 완료 응답이 유실돼도 최초 pending의 시작 단계를 다시 읽어 서비스 무변경을 유지한다. `services_untouched`가 있으면 불필요한 서버 간 조회와 서비스 재개를 호출하지 않는다. 외부 파일 변경·부정확한 승인·바뀐 CID/보호 설정은 임의 채택하지 않는다.

캐시42에는 기존40검사가 포함된다. 같은 시험을 플랫폼별로 합산해 독립 사건 수·탐지율로 표시하지 않는다. 기존 읽기/판정8파일과 동결 원장은 보존했다.

실제 B Docker는 `/usr/local/bin/docker`였다. 첫 Linux 드라이버는 `/usr/bin/docker`를 가정했고 컨테이너 생성 전에 실패했다. 관리자 경유 읽기로 경로·소유권·해시를 확인해 후보를 고쳤다. 재현기에서는 Mac 임시 폴더 그룹 상속·격리 소스의 `/check` 경로·잘못 사용한 `Path.chown`도 실패했다. 보호 검사를 완화하지 않고 전용 임시 폴더·경로 판정·`os.chown` 호출을 고쳐 최종 동결본 회귀를 마쳤다. 실패 원문과 수정 근거는 로컬 원장에 보존한다.

## 재현 순서

기존 Python과 보존한 공식 `G_Harness2/`를 사용한다. 구조 검사 뒤 같은 소스 SHA로 회귀를 실행한다. 출력 경로는 아직 없어야 하며 저장소 밖에 둔다. 회귀는 일반 사용자로 실행한다.

```sh
python3 -B infra/validation/journal-composition/reproduce_limits.py --repo . --output /private/tmp/soc-coordinator-baseline
python3 -B infra/validation/journal-composition/check_coordinator_structure.py --repo . --restored-root /private/tmp/soc-coordinator-baseline/candidate --output /private/tmp/soc-coordinator-harness2.json
python3 -B infra/validation/journal-composition/run_coordinator_regressions.py --output /private/tmp/soc-coordinator-checks
```

구조 검사는30파일 SHA·기존8파일·복원한2,271파일 후보·프레임워크 버전을 확인한다. 회귀는 예상 시험 수·종료 코드·생략·소스 불변·자체 임시 폴더 제거를 검사하고 로그와 `results.json`을 남긴다. 실패·시간 초과·검사 수 차이·미정리는 통과가 아니다. root 운영 CLI의 성공 실행이나 실제 독립 원복을 시험하는 명령은 아니다.

## 운영 적용 전 남은 조건

1. 임시 reader/MCP 차단기·제어 문서 정리와 현재 설치 출처 검증을 연결한다. 기존 영수증 불일치를 과거부터 정상이었던 것처럼 고치지 않는다.
2. 실제 systemd·부팅 차단·독립 복구·부분 실패·고정 root 진입점을 검증하고 현재 소스/모델/MCP 스키마/권한과 전체 payload를 고정한다.
3. 새 정확 후보의 관리자 승인 후 관리자231 경유로 적용한다. 새 수집·MCP·두 봇 새 채팅·의미/누락·로드·확정·복구를 확인한다. 이전 관리19/journal9 승인은 재사용하지 않는다.
