# Mattermost 분할 표와 실제 근거 기반 페이지

2026-11-04. 공통 계약 **1.5.19**, Native query **1.19.14**, context **1.0.1**을 운영 B에 반영·14:26:57 KST 확정했다. 원본35B·기존 MCP/승인 권한은 유지한다. [현재 상태](../../STATUS.md) · [검증 원장](chat-table-chunks-validation-20261104.json) · [앞선 대화 검증](firewall-chat.md).

## 문제와 변경

같은 OUTPUT 조회의 첫 표시 페이지16행이 Hermes에서 4,000자 경계로 나뉘며14행만 표로 해석되고2행은 머리글 없는 텍스트였다. `chat_markdown.split_tables`가 정상적인 최상위 파이프 표의 행 경계에서 나누고 동일한 머리글·구분선을 반복한다. 셀·순서·조건·handle·표시 행 수를 줄이지 않는다. 여러 메시지의 순번은 표 밖 문단에 놓고 길이 예산에 포함한다.

기존 source-pinned Mattermost 연결 훅에서 해당 어댑터 **인스턴스**의 분할 함수만 연결한다. 원래 send·언어/인용 guard·게시/재시도·스레드/메타데이터 처리는 유지한다. 다른 플랫폼과 표 없는 메시지는 원래 분할기를 사용하며, 코드펜스·비정상 표는 추정해서 바꾸지 않는다. 중복 연결은 재설치하지 않고 plugin unload 시 자기 훅만 원래 상태로 복구한다.

추가 실제 `다음 페이지` 시험에서는 기존 모델 생성 응답에서 Ollama가 존재하지 않는3규칙을 제시했고, Hermes는3규칙 중1개 조건 및 참조 집합 설명을 잘못 썼다. 공통 하네스의 페이지 요청 인식/조회 재사용 경로가 빠져 있었다. 이제 `다음 페이지`·`이전 페이지`·`첫 페이지`·`2페이지`는 같은 사용자/대화의 연속된 요청에서 범위와 표시 페이지를 계산한다. 확인된 실제 MCP 영수증을 검증한 뒤 공통 표시기로 재구성하며, 앞선 관측 시각과 **새 조회 없음**을 표시한다. 새로운 조회·대상 변경·쓰기·잘린 이력·실패/변조 영수증을 이전 성공으로 건너뛰지 않는다. 새 대화에서 대상 없는 페이지 요청은 한 번 확인하고 조회/모델을 호출하지 않는다.

이 처리는 관측을 새로 만들거나 사건 위험을 고정 분기로 판단하는 기능이 아니다. 새 상태 확인은 여전히 LLM이 허용된 읽기 도구를 선택하고, 변경은 기존 정확 후보·관리자 승인·worker 검증을 따른다.

표 구문 검증은 [Mattermost marked 고정 소스](https://github.com/mattermost/marked/blob/467bc9e99fc75d69424188dfbea7fe0409a9fc15/lib/marked.js), SHA256 `7a7e73ca0aad7145c2c38ff4d02ae431c264221f6fa1771dfa662f125e60789c`·36,485B·MIT를 사용했다. 기존 Node로 검사했고 임시 다운로드는 제거한다. 이는 설치된 프런트엔드 버전/실제 브라우저 화면 검증을 대신하지 않는다. 하나의 머리글+행 자체가 메시지 예산을 넘으면 기존 분할기로 반환한다. 이 경우 데이터가 없어지는 새 동작은 없지만 표 형식은 보장하지 못한다. 기존 FW 표시기의 초장문 표시 생략 표식·MCP 전체 원문 보존도 별도 한계다. 위19행의 무생략 확인을 모든 보안장비·모든 길이·모든 자연어/사건 판단으로 확대하지 않는다.

## 설치 연결과 복구

루트 `deploy.sh`의 기존 SIEM `hermes_extension_files`, Ollama `source_bundle`, review source 목록이 canonical `chat_markdown.py`와 기존 query/health/harness/contract를 복사한다. 추가 패키지·이미지·포트·설정 키·권한은 없다. 기존 서버에는 전체 설치기를 실행하지 않았다. 설치기 자체의 미수정 문제와 새3VM 전체 시험 보류는 [초기 설치 점검](../../deployment/INSTALLER_READINESS.md)을 따른다.

원본/소유권·모드·중간/최종 후보 SHA/검증은 B의 `/var/lib/capstone-table-chunks/20261104-r1/deployment`에 있다.14:14 표 분할·14:22 페이지 보완으로 유휴 확인 후 기존 실행부를 각 단계1회 재시작했다. 원래14파일 복구본과 중간 receipt SHA도 보존하고15분 독립 원복 타이머를 실제 검증 후 해제했다. 확정된 복구의 no-op만 검사했으며 실제 수동 원복은 실행하지 않았다.

관리자가 복구할 때는 같은 관리자231→A→B 경로에서 `python3 -B /var/lib/capstone-table-chunks/20261104-r1/deployment/rollback.py --manual`을 사용한다. 활성 요청이면60초 뒤 독립 실행으로 미루고, 자신이 바꾼 SHA만 원본으로 복원하며 동시 변경은 덮어쓰지 않는다. 운영 DB/큐/WAL·대화 원문을 복원·삭제하지 않는다. 이전 시험 오답은 보존하고 같은 스레드에 실제 재조회 정정 응답을 추가했다.

원문 API/DB/파서 결과와 시험 질문은 로컬 전용이며 학습에 넣지 않았다. Git 게시와 임시 정리 상태는 [STATUS](../../STATUS.md)와 작은 원장에서 구분한다.
