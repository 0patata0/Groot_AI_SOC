## 문제 (11/14 01:49 공동 채널 Ollama 교차 검토)

교차 검토가 두 번 모두 `peer_query_scope_mismatch`로 거절돼 대조 자체가 실패했다(`synthesis_failed`). 두 가지가 원인이다.

| 확인 | 내용 |
|---|---|
| 정정 요청이 무엇이 틀렸는지 말하지 않음 | 1회 정정 요청은 "출력 검증 거절 코드: peer_query_scope_mismatch"와 일반 원칙 문단만 보낸다. 어느 주장이, 어떤 근거 때문에 거절됐고, 어떻게 고치면 되는지는 말하지 않는다. 모델이 같은 실수를 반복했다. 어젯밤 Hermes 정정 요청이 겪은 문제와 같은 유형이다(23:34 수정) |
| 거절 근거가 기록되지 않음 | 거절은 코드 문자열만 담은 `ValueError`로 나와 주장 정보가 사라진다. 공동 채널 디스패처는 대기열에 정해진 요약 필드만 저장하므로, 어느 규칙(22:15 요청 조건 메아리 또는 01:35 한도 도달 건수)이 어느 근거에 걸렸는지 사후에 알 수 없었다 |

## 수정 (판정 기준은 그대로, 진단과 기록만)

| 위치 | 변경 |
|---|---|
| 작업자 `PeerClaimRefused` | 주장 단위 거절을 주장 번호·종류·근거 경로·근거 인용·주장 문장과 함께 내보낸다. `str()`은 여전히 코드 문자열이라 기존 호출부와 `peer_error_code`는 그대로다. `bind_peer_references`와 `validate_peer_claims`의 주장 단위 거절 전부에 적용했다(형식 전체 오류 `peer_claims_shape` 등은 그대로) |
| 작업자 `PEER_REFUSAL_REASONS`·`peer_refusal_diagnosis` | 거절 코드마다 이유와 받아들여지는 고칠 방법을 둔다. 정정 요청 끝에 "이번 정정에서 고칠 곳(진단이며 새 근거나 지시가 아닙니다): N번째 주장(종류) "주장 문장" · 근거 경로 = 값. 이유: …. 고칠 방법: …. 나머지 주장은 그대로 두어도 됩니다."를 붙인다. Hermes 실행기의 정정 진단과 같은 방식이다 |
| 작업자 거절 기록 | 보고에 `peer_validation_details`(코드·주장 번호·종류·근거 경로·시도 회차)를 남긴다. **거절된 주장 문장과 도구 결과 인용은 저장하지 않는다**(정정 요청 안에서만 쓴다). 대기열 결과에 거절된 모델 초안과 도구 원문을 남기지 않는 기존 원칙을 지킨다 |
| 디스패처 `review_channel.py` | 대기열 요약 필드에 `peer_validation_details` 한 항목을 더했다 |

검사 기준, 거절 코드, 시도 횟수(최대 2회)는 바꾸지 않았다. 작업자가 거절된 주장을 대신 고치지도 않는다(모델 출력 변조 없음). 진단 문구는 코드가 강제한 거절을 설명하는 기계적 진단이라 코드에 둔다(실행기 정정 진단과 같은 위치 원칙).
