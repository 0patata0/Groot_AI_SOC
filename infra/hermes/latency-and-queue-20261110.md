## 1. 채팅 응답 지연 (룰 수정·추가 문의 포함)

오늘 B 리뷰 채널 실제 요청(Ollama SDK 경로)의 모델 호출 기록(`ollama` 응답 필드):

| 11:20 | 룰 추가 간단 테스트 | 37.9초 | 30.1초 | 23,413 | 22.2초 | 7.5초 | 0초 |

- MCP 도구 실행은 0.1~0.25초다. 지연의 대부분은 **모델의 입력 처리**(약 1,060토큰/초)와 **Thor 대기열 대기**다.
- 도구를 고르는 첫 모델 호출이 정책 문서(Ollama 시스템 프롬프트 28,073자)와 **45개 도구 정의 전체**를 매번 함께 보낸다. 런타임은 시작 시 모든 도구를 바인딩하며, 질문 유형별 `tool_scope`는 첫 호출의 바인딩에는 쓰이지 않는다.
- Thor(Ollama 0.40.2, llama.cpp)는 **단일 슬롯**(`id 0`)으로 한 번에 한 요청만 처리한다. 다른 요청이 처리 중이면 대기한다.
- 이 모델(qwen35moe, 하이브리드 구조)은 체크포인트 위치에서만 이전 입력 상태를 재사용한다. 로그에 `forcing full prompt re-processing`이 15회(최근 1시간) 기록됐다.
- B의 모델 상태 점검(`capstone-soc-model.timer` → `soc_monitor.py model`)이 약 3분마다 15토큰짜리 `/api/generate`("Reply OK.")를 보낸다(최근 1시간 20회). 단일 슬롯에서 이 요청이 직전 채팅 상태를 덮어써, 다음 채팅 요청은 2.2만 토큰 입력을 처음부터 다시 처리한다.
- A의 룰 실행기(`rule-change-executor`)는 오늘 83회 평균 2.4~2.5초였으나 최대 41초(12:01 실제 변경 적용), 읽기 전용 25초(12:02) 사례가 있었다. 변경 적용 시 suricata 재기동(12:02:39)이 동반됐다.

## 2. "에이전트 큐가 가득 찼다" (Wazuh 에이전트 버퍼)

| 에이전트 | 포화 경보(203) | 시각(KST) | 원인 |
|---|---|---|---|
| groot-siem-host (B) | 11/8 22:21, 11/9 10:22·22:23, 11/10 10:24 | 약 12시간 간격 | rootcheck 정기 점검 시작 직후 4초 안에 버퍼 90%→가득 참, 6초 뒤 정상 복귀 |

- B 에이전트 로그: `10:24:30 rootcheck: Starting` → `10:24:34 Agent buffer is full: Events may be lost` → `10:24:40 under 70%` → `10:25:25 Ending rootcheck`.

- 그 6초 동안 일반 보안 이벤트(journald 등)가 유실될 수 있다. A의 공격 시험일 포화는 IDS·WAF 이벤트 유실 가능성이 있어 더 중요하다.

### 적용 결과 (B, 18:44:42 KST, 사용자 승인)

- 설치기 `deployment/siem_host_agent.py`에 `tuned_buffer`(queue_size 20000·events_per_second 1000)를 추가해 새 설치 설정 후보와 기존 설치용 `tune-buffer` 동작이 같은 코드를 쓴다. 기존 설치는 영수증 검증→백업(`ossec.conf.before-buffer-20261110T184442`)→문법 검사→재시작→연결 확인→영수증 `config_sha256` 재결속 순서이며 실패 시 원래 설정으로 복원한다.
- 적용 후 매니저에서 3개 에이전트 Active. 재시작 직후 시작 시 점검(`scan_on_start`) 일괄 전송으로 18:44:52에 한 번 포화했다가 7초 뒤 회복했다(일회성). 12시간 주기 rootcheck 포화 해소 여부는 다음 실행(약 22:25 KST)에서 확인해야 한다.
- A는 미적용(수집 가드 고정값 동시 갱신 필요).

### 개선 후보 (미적용, A)

- B: `siem_host_agent.py`의 설정 후보에 `client_buffer`(예: queue_size 20000, events_per_second 1000)를 추가하고, 기존 설치의 영수증(`config_sha256`)을 함께 갱신하는 변경 경로를 만든다.
- A: 에이전트 설정 SHA가 raw 로그 이전 가드의 고정값(`wazuh_config_sha256`)에 묶여 있어, 같은 변경 단계에서 고정값을 갱신해야 한다. 그렇지 않으면 수집 가드가 Vector/Wazuh 읽기를 보류한다.
