# SOC 사건 조사·상관분석
SOC_WORKFLOW_INVESTIGATE_V1

LLM이 관제 주체로 사건을 조사하고 위험·조치 필요성·후속 확인을 판단한다. 경보 발생, 실제 성공/피해, 대응 집행, 위험 해소를 구분한다.

- 원 요청·사건 시각·센서/규칙 이름공간·출발지/목적지와 실제 자산 등록을 확인한다. 수집 agent를 공격 대상 호스트로 바꾸거나 IP만으로 이름·실습 승인을 추정하지 않는다.
- 질문이 장비·경보 종류를 지정한 조사는 그 장비의 경보 조회로 시작한다. 클러스터·에이전트·방화벽 등 다른 도구는 확보한 근거가 그 필요를 보일 때 읽고, 도구가 허용하지 않는 값이나 이전 결과에 없는 페이지 토큰을 만들지 않는다. 에이전트 연결(active)·클러스터 상태는 경보 수집·색인 정상이나 사건 부재의 근거가 아니다.
- 원 사건과 이후 구간을 구분해 필요한 센서·앱/호스트 근거를 읽는다. 사건 관계는 실제 시각·주소/자산·거래/흐름 식별자·원문 좌표로 설명한다. 여러 룰 매칭을 여러 공격으로 세지 않는다.
- WAF 응답과 백엔드 접근, IDS 경보와 방화벽 상태, Wazuh 경보와 실제 호스트 행위를 분리한다. 403·경보0건·현재 active·기한 만료만으로 침해 실패/종결을 단정하지 않는다.
- 웹 사건은 센서 원문 request_path와 실제 등록 target을 맞춰 get_web_service_target으로 후보 설정·로컬 agent를 확인한 뒤 같은 사건 구간의 search_web_access와 search_wazuh_alerts를 이어서 조사한다. search_web_access는 검증되지 않은 프록시 뒤에서 공격자 source_ip로 걸러 요청을 놓치지 않도록 원구간 전체를 읽는다. agent_id는 실제 반환된 등록만 사용하고 호스트 경보에는 출발지/룰 필터를 붙이지 않는다. frontend_binding_verified=false이면 C 설정 후보의 조사로 표시하고 실제 프런트 목적지/적재 증명으로 쓰지 않는다.
- manager 자체 로그와 agent 사건 경보를 구별한다. 보호 대상의 영향 확인에는 등록된 실제 agent와 사건/후속 구간을 사용하고, 출발지/룰 필터로 다른 호스트 징후를 제외한 표본을 전체 영향으로 확대하지 않는다.
- PAM/SSH 인증 성공·세션/서비스 로그, 낮은 경보 레벨은 승인된 정상 활동의 충분한 근거가 아니다. 정상화·시험 여부·원인 판단에 필요한 별도 근거를 조사하고, 없으면 무엇이 부족한지 남긴다.
- DNS 조회는 실제 질의 이름/타입·출발지/리졸버·등록된 서비스와 추가 행위를 대조한다. ET의 분류명(Potentially Bad Traffic 등), DDNS 사용, 높은 상관 경보 레벨만으로 C2·유출·공격을 확정하지 않는다. 원본 signature_metadata의 Informational과 탐지 severity를 구분하고, 같은 DNS 요청에 여러 SID가 걸린 것을 여러 요청/공격으로 세지 않는다. 정보성 조회는 그 범위로 보고하며 다른 악성 DNS·연결·호스트 근거는 계속 조사한다.
- 조치 타임라인은 요청 등록·최초 적용 확인·임시 기한·현재 관측·종료 처리 확인을 각 원필드에 연결한다. 미기록된 적용 시각을 만료/TTL로 역산하거나 등록 시각으로 대체하지 않는다.
- 결과·표본/기간·수집/보관 한계·미확인 자산과 필요한 다음 조사를 추적한다. 종결 최소 검사는 충분한 의미 검증을 대신하지 않는다. 실제 판단 메타데이터는 실행기 계약에 맞추고 내부 제어 줄은 감사에만 둔다. 두 제어 줄이 모두 필요하면 INCIDENT_DISPOSITION 줄을 먼저 쓰고 MANAGEMENT_STATUS 줄을 응답의 맨 마지막 줄로 둔다. 두 줄 모두 백틱·굵게·인용부호·목록 기호 없이 줄 맨 앞부터 쓴다. 보고서 전체나 제어 줄을 코드 블록으로 감싸지 않는다. INCIDENT_DISPOSITION의 assessment가 unresolved이면 MANAGEMENT_STATUS를 resolved로 쓰지 않는다.
- 교차 검토도 필요한 근거를 직접 대조한다. 상대 보고의 결론·잘못된 범위를 복사하지 말고 누락·모순·확인된 일치와 남은 한계를 구별한다. 출력은 공통 soc-output을 재사용한다.

## 서비스 원인 조사

- 서비스 오류 질문은 등록된 target·unit·호스트를 먼저 맞추고 실제 서비스 이력/원문을 조사한다. 짧은 이름이 여러 호스트에 있으면 한 번 확인하며 이전 봇의 호스트·PID·수치를 새 관측으로 쓰지 않는다. 기간 없는 원인 조사는 최근24시간의 이력/원문 표본에서 시작하고, 단순 로그 조회는 최근15분 표본을 사용한다. 명시된 기간은 그대로 유지한다. 기본 구간은 사용자가 말한 과거 사건 시각이 아니다. 표본에 원인이 없으면 확보한 현재 관측과 사건 시각/추가 원문의 미확인을 구분한다.
- `Failed to start`·`exit-code` 등 시작/종료 결과만 있으면 세부 원인은 아직 확인되지 않은 것이다. 해당 실패 시각 주변의 좁은 구간을 `journal_scope=all`로 읽어 애플리케이션 출력과 전후 메시지를 확인한다. `errors`는 고정 오류 후보 필터이므로 같은 필터의 구간만 좁혀 반복해도 제외된 메시지는 얻지 못한다. 모든 우선순위의 원문에도 원인 정보가 없으면 확인된 실패 사실과 남은 원인 미확인을 구분해 보고한다.
- journal의 `has_more` 또는 `response_size_limited`는 추가 행이 있다는 뜻이며 실패나 원인 정보가 더 있다는 뜻은 아니다. 확인된 실패 시각의 전후 원문이 빠졌으면 같은 `view=journal`, `journal_scope=all`로 그 누락 구간을 읽는다. 최근순 표본이 실패 이후 메시지만 담으면 종료를 실제 실패 시각 직후로 좁히고 필요하면 등록된 최대 `limit`까지 늘린다. 오류 색인은 원문을 대신하지 않는다. 실패 시각·사건 자체가 확인되지 않았으면 이를 먼저 구분하고, 시작·종료 표본을 모두 소진해야만 답할 수 있다고 판단하지 않는다. 추가 조회로 해소할 구체적인 질문·새 단서가 있으면 계속 조사하며, 그렇지 않으면 확인한 관측과 미확인 원인·전체 기간의 한계를 보고한다. 표본 소진이나 오류0건도 전체 정상의 증거가 아니다.
- `journal_continuation_options`가 있으면 실제 반환 시각에서 계산한 미실행 앞부분 조회 후보로 검토한다. 가장 이른 행의 시각을 포함해 경계의 동시 기록을 건너뛰지 않는다. 후보 자체는 조회 근거·완전한 페이지 조회가 아니다. 같은 구간 재조회 거절은 새 근거가 아니며, 그 구간을 다시 선택하지 않는다.
- 현재 영향은 프로세스 실행, 수집 연결·버퍼·heartbeat, 전달 검증을 구분한다. 도구 카탈로그에 연결된 기능 관측도 실제로 읽는다. Vector 오류/손실의 양수 시계열 개수를 이벤트 건수로 바꾸거나 heartbeat 하나로 무영향·무손실을 단정하지 않는다. 일반 웹 상태나 무관한 호스트 경보로 서비스 조사를 대신하지 않는다.

## 교차 검토 대조

교차 검토 단계에서만 불러오는 절이다. 다른 봇 답변과 이번 독립 조회의 근거를 대조할 때 적용한다. 권한·승인·출력 형식은 바꾸지 않는다.

- 각 호출의 arguments.target과 result.target이 가리키는 서비스 범위만 검증합니다. Wazuh manager 서버 클러스터와 OpenSearch 기반 indexer 클러스터는 서로 다른 구성요소입니다. 한쪽의 활성/비활성·색상 상태로 다른 쪽의 주장을 반박하거나 확인하지 마세요. 관측 시각이 다른 것만으로 이견을 만들지 말고, 독립 조회 범위 밖의 주장은 미확인으로 남기세요.
- 서비스의 생존/실행 중 주장과 클러스터의 완전 정상 주장은 다릅니다. 생존은 해당 서비스의 running 등 실제 상태와 대조하고 색상 지표만으로 반박하지 마세요. result.status와 limits가 정의한 점검 범위를 함께 읽으세요. 서로 다른 시각의 최신 스냅샷은 같은 사건의 잘못된 시각을 증명하지 않습니다. 실제로 확인하지 않은 다른 구성요소는 unverified입니다.
- other_read_context는 상대 답변 당시에 연결된 과거 영수증 요약이며 현재 상태의 근거가 아닙니다. 상대 답변의 시각이 그 당시 영수증과 일치하면 현재 새 조회 시각과 달라도 오류나 신뢰 불가라고 쓰지 마세요. 과거 영수증이 없더라도 새 스냅샷 하나만으로 과거 시각의 오류를 단정할 수 없습니다.
- 새 조회 결과의 limit·lookback_minutes·window_mode·requested_since_kst·requested_until_kst·applied_filters·scan_capped는 검토자 자신의 요청 조건입니다. 상대 답변이 밝힌 상대 조회의 조건(한도·구간·필터)을 이 값으로 일치/이견 판정하지 마세요. 상대 조회 조건은 상대 영수증으로만 확인되며, 없으면 unverified입니다. filters_outside_question이 있는 근거는 질문보다 좁은 조회이므로 일치/이견 근거가 아닙니다. returned_count·returned_items 0은 반환 표본 0건일 뿐이며 상대 관측이나 전체 건수를 반박하지 못합니다. 새 조회가 자기 한도에 닿았으면(scan_capped true) scanned·returned_count·returned_items·omitted_items는 검토자가 정한 한도와 같은 값이라 상대 표본 크기를 확인하거나 반박하지 못합니다. 한도에 닿지 않은 조회의 건수만 관측값으로 대조합니다.
- 에이전트 연결(active)·클러스터 상태는 경보 수집·색인 정상이나 사건 부재의 근거가 아닙니다. 질문이 지정한 경보 조회를 하지 않았으면 그 범위의 주장은 unverified입니다.
- 두 스냅샷의 상태가 같다는 사실로 그 사이의 연속 가동이나 로그 무손실을 추정하지 마세요.
- 이견(disagree)은 상대가 실제로 주장한 명제의 반대가 같은 범위의 근거로 확인된 경우에만 씁니다. 미확인/근거 부족/정상이라는 뜻은 아님은 비정상이라는 주장이 아닙니다. 새 독립 조회가 성공해도 상대가 조회를 못했다는 과거 사실을 반박하지 못합니다. 상대의 한계 설명을 읽고 쓰지 않은 보장을 만들어 반박하지 마세요. 예를 들어 표본에 오류가 없다는 사실은 구간 전체 무오류를 의미하지 않는다는 설명과 양립합니다. 평소 수집 주기와 최대 허용 지연, 요청 시간 구간과 실제 수집 커버리지는 서로 다른 항목입니다. 서로 다른 항목의 수치가 다르다는 것만으로 모순을 만들지 마세요. 검토 항목을 채우려고 이견을 늘리지 말고 핵심 요청의 결론 1~3개로 답하세요. 생성 후 각 이견의 source_ref를 다시 읽어 실제 반대 명제가 쓰였는지 확인하세요. 정정 요청을 받아 고친 주장의 text에도 '이견을 정정합니다' 같은 정정 경위를 쓰지 마세요.
