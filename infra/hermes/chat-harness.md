ID/상태를 고정 답으로 저장하지 않고 반환 이름·ID로 대조하며 B host와 Wazuh Manager를 구분한다. 명시한 상태가 없으면 active부터 보고 대상이 없을 때 다른 상태를 확인하며 전체 목록은4상태를 요구한다. 이름/IP 필터를 추측하지 않고 대상 중복·실패·누락·페이지 밖은 미확인으로 남긴다. 상태 아이콘은 표시 장식으로만 처리하고 상태 토큰은 검증한다. 공통 renderer는 요청 대상만 표로 표시하며 모델이 실제 도구·인자를 선택한다. 공동 Hermes에도 같은 대상 안내를 전달하고 조회 범위 누락은 partial로 보존한다. ID·연결 상태의 상호 검토는 각 모델의 새 조회와 상대 표의 ID/이름/상태를 직접 대조한다. 서로 다른 시점의 값 차이는 원인을 단정하지 않고 표시하며, 표 누락·중복·잘림·독립 조회 부족은 검토 미완료다. 다른 서술이나 보안 정상 판단까지 검증했다고 확대하지 않는다. 실제 반환이 요청한 정확한 이름과 일치하는 이름 필터 조회는 해당 대상만의 근거로 인정하며 전체 목록의 근거로 재사용하지 않는다. 모델/보호 권한·승인 경계는 유지하며 [실채팅 결과·잔여](../../STATUS.md)를 따른다.


## 짧은 규칙 질문 — 계약1.4.13 / query1.11.13

- `FW 룰`, `방화벽 보여줘`, `fw 률 츌력해볼래`는 네트워크 방화벽 범위를 유지한다. 현재 전체 FW 조회 도구는 미구현이므로 미조회·미완료와 기본 정책/NAT 누락을 명시한다. WAF/IDS 커스텀 파일이나 임시 `list_blocks`를 전체 FW 조회로 대체하지 않는다.
- `WAF 룰`, `IPS 룰`, `와주 룰` 등 명확한 장비+항목을 읽기 요청으로 처리한다. IPS 별칭은 Suricata를 가리키며 실제 인라인 차단 여부를 뜻하지 않는다. 도구·인자는 모델이 선택하며 값은 실제 조회 근거를 사용한다.
- 문맥 없는 `룰 보여줘`는 대상 확인 질문 한 번으로 끝낸다. `WAF 기본 룰`은 커스텀 규칙을 대신 보여주지 않는다. 전체 요청에 커스텀 파일만 조회할 수 있으면 답변 첫머리에 미확인 범위를 표시한다. 명시한 여러 장비와 제외한 장비를 구분한다.
- 범위 확인/미지원 안내는 서버 조회 성공이 아니다. 두 일반 채팅과 공동채널은 해당 안내에 모델·MCP 호출을 추가하지 않으며, 공동채널은 같은 안내만 되풀이할 자동 교차 검토를 생략한다. 실제 불확실 사건·변경·명시적 교차 검토의 기존 경계는 유지한다.
- 원 질문·원본 도구 결과는 수정하지 않는다. 조회 분류용 별칭·제한된 오타 보정은 쓰기 승인이나 변경 의도를 만들지 않는다. 교차 검토는 상대의 장비 해석보다 원질문의 장비·기본/커스텀/전체 범위를 먼저 대조한다.

배포·실채팅 검증 여부와 미구현 FW 전체 조회는 [STATUS](../../STATUS.md)를 기준으로 한다. 일반 자연어 전체의 의미 정확도나 기본/전체 규칙 관제 완료를 보장하지 않는다. 초기 설치기는 기존 공통 소스 배치 경로를 사용하며 추가 패키지·포트·키·sudo 권한은 없다.

- 장비와 뒤따르는 요청 항목·필터·최대 개수를 묶는다. `A 프로세스 2개, C UDP 포트 4개`를 네 가지 조합으로 늘리지 않으며, 명시한 여러 agent ID를 모두 추적한다. 제외한 장비는 읽기 범위에서 제거하되 원본 질문과 쓰기 의도 검사는 보존한다.
- 실제 에이전트 목록으로 이름을 확인하고, 알 수 없는 이름을 다른 ID로 대체하지 않는다. 명시한 프로세스 이름/명령줄 포함 검색과 명령줄 미제공 표시를 지원한다. 임의 필터나 해석하지 못한 문장은 일반 에이전트 경로로 남는다.
- 모델에 제공하는 JSON Schema에서 장비·필터·한도를 `anyOf`로 함께 제한한다. 도구와 인자는 같은35B 모델이 선택하며 서버의 값·개수·상태를 답변 상수로 넣지 않는다. 표와 미지원 설명의 형식은 공유 코드로 만든다.
- 상태별 개수/ID 요약 표, 파일 정의 개수 비교, 장비별 취약점 분포와 수집기 통계의 별도 범위를 지원한다. 표본 개수를 전체 취약점 분포의 제한으로 전파하지 않는다.
- 서비스 진단은 실제 연결 도구의 대상 enum과 요청을 대조한다. 현재 `b:hermes`, `b:wazuh-manager`는 이 진단 목록에 없으며 `b:soc-bot`을 Hermes로 간주하지 않는다. 이 경우 실제 상태 조회0·미지원/미확인으로 답한다. 별도 룰 서비스 조회의 Wazuh 대상 존재와 systemd 진단 지원은 구분한다.
- 일반 읽기에서 근거 없는 완료 문장이 나오면 Hermes에도 공통 근거 검사를 적용한다. 해석 가능한 범위의 누락 검증이며 임의 자연어 전체의 의미 정확도를 보장하지 않는다.

평가는 수정에 쓰는 질문과 미리 보류한 별도 질문을 분리하고, 매회 새 스레드·양쪽 교대 순서·코드 고정 조건에서 반복한다. 수정 전 실패와 미지원 설명을 성공한 실제 진단으로 바꾸지 않는다. 하네스 변경 뒤 쓰기·실제 공격 E2E·새 서버 전체 설치 검증은 각각 별도다.

## 실행부에 남는 차이

- Hermes의 native iteration은 API 재시도·로컬 표시 단계·grace 처리와 관계가 있다. Ollama의 실제 모델 호출 카운터12회와 엄밀히 같은 단위가 아니다. Ollama의 별도 도구32회 한도를 Hermes에도 동일하게 강제했다고 주장하지 않는다.
- 명확한 읽기 계획·룰 목록/IDS 구동·전체 진단에서 양쪽 모두 첫 단계부터 같은 모델의 JSON Schema 선택을 검증한다. Hermes는 native tool-call 형식, Ollama는 기존 SDK adapter로 실행한다. 일반 대화·분석·보호 작업은 각각 기존 실행부를 따른다. 모델이 도구·인자를 선택하며 고정 분기로 대신 조회하거나 보호 작업을 자동 재실행하지 않는다. Hermes 선택 단계의32호출 상한은 전체 native 경로의 통일을 뜻하지 않는다.
- Hermes의 취소·연결 재시도·종료·저장은 native 경로를 따른다. Ollama는 SQLite 작업 큐와 동일 보호 인자 중복 실행 방지를 별도로 유지한다. 승인·증거·TTL·보호 주소 검사는 같은 서버가 강제한다. 일반 대화나 두 봇의 합의로 승인하지 않는다.
- Hermes의 `resp`는 읽기 `list_blocks`와 보호 작업이 같은 서버에 있으므로 서버 단위720초다. Ollama는 해당 읽기 호출에는90초를 적용한다. 접속/모델 HTTP/전체 턴 취소 한도도 native 차이가 남는다. Ollama 첫 실행900초·정정180초·gateway1110초는 응답 목표 시간이 아닌 실패 상한이다.
- 변경안 표는 **이번 요청에서 확인한 제출 근거**다. 제출 당시 pending을 현재 적용 완료로 바꾸지 않는다. 오류·통신 두절을 미적용으로 단정하지 않으며 상태 재조회가 필요하다. 적용/원복 성공은 기존 상태 조회와 실제 SHA·런타임 확인을 별도로 요구한다. 임의 자연어의 모든 목적·영향·원복 설명을 완전히 검증하는 의미 분석기는 아니다.
- 자동 사건 관리 controller는 Hermes만 담당하며 이번 일반 Mattermost 채팅 옵션 정렬에서 제외한다. 자동관리 이관·동시 사건 소비·모델 교체는 하지 않았다.

## 2026-10-25 확장 조회 수정

[read_contract.py](read_contract.py)는 열거 부정문, 요청별 누락 항목, 실제 이름→ID 식별, 응답 범위와 표시를 두 실행부에서 공유한다. 인용된 명령·정책 설명을 실행 지시로 바꾸지 않으며, 금지문 뒤의 실제 변경안 작성 지시는 유지한다. 성공한 같은 조회의 반복을 줄이고 해시가 검증된 실제 도구 결과만 사용한다.

- `9999` 특수 연결 시각은 미확인으로 표시해 KST 변환 overflow를 막는다. 실행 시작/마지막 연결/조회 시각을 서로 대신하지 않는다.
- 취약점 요약은 반환된 전체 목록의 심각도를 집계하고 Critical 표는 요청한 최대 개수(기본5, 상한100)를 지킨다. 전체 설치 수·페이지 완전성·미제공 CVE/패키지/버전은 미확인이다. Ollama의 해당 응답만8MiB까지 수용하며 다른 응답은2MiB 상한을 유지한다.
- Hermes는 정확한 `wazuh-ro.get_wazuh_vulnerability_summary` 결과를 native 2,000,000자 절단 전에 같은 순수 집계기로 처리한다. 전체 반환 레코드 수·분포·원문 SHA/바이트 수를 보관하며 native flood cap은 유지한다. 이 출력 어댑터는 같은 프로세스의 해당 읽기 결과에만 적용되고 새 호출/재시도/권한을 만들지 않는다. 원문 전문은 Hermes 대화에 중복 저장하지 않는다. 8MiB 초과·예상 밖 형식은 기존 제한을 따르며 절단 표식이 있으면 부분 집계/미완료를 보고한다.
- Hermes native 분리 결과는 현재 호출 ID와 정확한 전용 cache 파일, 소유권·권한·크기·해시를 검증해 감사/표시에 포함한다. 일반 파일 도구 권한은 추가하지 않는다.
- 과거 제안의 `result`가 있어도 `status`/`proposal_id`를 잃지 않는다. 과거 실패와 현재 파일/컨테이너를 따로 표시한다. 정확한 사전 anchor 검사 거절 뒤 유효 제출은 해결된 재시도로 구분하지만, 결과 미상·통신 오류는 해결로 추정하지 않는다.
- 같은 스레드의 검증된 룰 목록 표 재정리는 기존 근거를 유지한다. “추가 조회는 하지 말고”는 새 조회 금지로 처리하며, 검증된 이전 근거가 없으면 미확인으로 끝낸다. 원래 파일 응답의 KST 생성 시각을 함께 표시한다. IDS가 local.rules를 사용하는지 묻는 질문은 파일 목록 대신 실제 구동 경로·ET+local 결합 근거를 읽는다. 정책 거절 설명에 조회를 강제하는 오탐을 줄였다.
- C 원본 수집기 현지 시각에 MCP가 Z를 붙이는 문제를 직접 확인했다. 해당 Global/Interval 시각은 시간대 검증 필요로 표시하고 카운터와 원본 감사 자료는 보존한다. 모든 호스트의 시간대를 KST로 가정하지 않는다. upstream formatter 수정은 별도 미완료다.

초기 설치와 증분 배포 소스를 동기화했다. 자동 사건 controller/관리 설정·Memory는 이번 배포에서 유지했다. 동일 함수의 canonical 변경과 운영 자동관리 실행 파일 교체를 혼동하지 않는다. 실제 채팅 재시험, 중간 실패 표본, 남은 쓰기/장기 평가 범위는 [STATUS](../../STATUS.md)에 기록한다.

## 2026-10-25 반복 시험 보완 — 1.9.2

동일 질문을 새 스레드에서3회씩 실행하자, 단일 C 조회의 성공만으로는 A·C 복합 요청의 누락을 막지 못한다는 점이 드러났다. `read_contract.py`는 알려진 장비 이름/별칭으로 요청을 분리하고 실제 에이전트 목록에서 확인한 ID만 다음 조회에 허용한다. 임의 이름을 ID로 추측하지 않는다. 한국어 조사가 붙은 `ID 999의`도 명시 ID로 인식하며 실제 반환값이 모호하면 장비 부재나 정상으로 확정하지 않는다.

- 미조회 장비·항목만 다음 선택 스키마에 남긴다. 동일한 도구/인자의 중복 선택은 전체 스키마 검증 후 하나로 줄인다. 다른 도구·인자를 만들어 보완하지 않으며 잘못된 선택은 거부한다.
- 규칙 개수와 IDS 실제 사용 여부를 함께 물으면 파일 정의 표와 실제 서비스 경로를 모두 표시한다. 한쪽이 없으면 전체 완료라고 하지 않는다. 개별 SID 적재·탐지 성공은 여전히 별도 검증 대상이다.
- 진단 대상은 실제 도구의 전체 enum을 보존한다. 대상과 스키마·해시가 맞는 결과만 완료로 인정하고 전체/확인/미조회 수를 표시한다.25대상은 한 선택 묶음에 담을 수 있지만 호출 예산32와 기존 실행 경계는 유지한다.
- `Wazuh Manager`와 물리 이름/별칭을 같은 장비 후보로 해석하되 ID는 실제 목록에서 확인한다. 상태 목록에 임의 name/limit 필터를 넣지 않고, 인벤토리 최대 개수는 실제 선택 인자에도 요구한다. 명시 프로세스 검색/필터 요청은 일반 실행 경로에 남기며 기본 인벤토리에 빈 `search`를 추가하지 않는다.
- UDP에 TCP의 LISTENING 상태를 추측해 넣지 않는다. 도구가 요구하는 protocol/state 문자열 중 사용자가 지정하지 않은 필터는 검증된 빈 문자열로 제한한다. 명시한 TCP 상태는 유지한다. `No network ports for agent …`도 원문 의미를 보존하고 자료 부재/수집 실패와 실제0건을 섞지 않는다.
- 최대 개수는 프로세스·포트·Critical 예시 조회에 적용한다. 별도 심각도 분포 조회에는 예시 개수/심각도 필터를 넣지 않는다. 제한된 분포 조회를 전체 요청 완료 근거로 인정하지 않는다.1.9.1에서 이 둘을 섞은 회귀를 발견했고1.9.2에서 수정했다. 당시 실패 표본은 보존한다.
- 시간 도구의 `reference`는 사건 ID가 아닌 실제 시각이다. 명시 기준이 있으면 그 원본 시각만 허용하고 반환 근거도 같은 기준인지 검사한다. 날짜·오프셋을 바꾸거나 모델이 암산해서 대신하지 않는다.
- Ollama 채팅 감사 기록은 큰 취약점 응답을 검증된 공통 집계로 축약해 원문 SHA/크기·집계 SHA·다른 조회·모델/전체 시간을 보존한다. 기존4MiB 저장 상한을 넘는 다른 자료는 생략 사유와 해시를 남긴다. 이전 기록의 생략된 원문을 복원했다고 주장하지 않는다.
- 유효한 오류 또는 등록 여부를 증명하지 못하는 빈 인벤토리 응답은 같은 호출을 무작정 반복하지 않는다. 오류 원문·미확인 범위를 표시한다. 이 처리는 upstream의 오류/빈 목록 혼합 자체를 고치는 것은 아니다.
- 보호 DGX 차단의 **정책 설명만** 요청한 경우, 현재 사용 가능한 두 차단 도구의 실제 설명과 일치하는 사실만 공통 양식으로 표시한다. 관리자 승인이 보호주소 제한을 우회하지 않는다고 밝히며 모델/조회 호출0이다. 도구 정의가 달라지거나 실제 사건 조사·조치를 함께 요구하면 이 경로를 쓰지 않는다. 사건 판단·관리 주체를 고정 분기로 대체하는 기능이 아니다.

같은 모델/권한의 수정 전후3회 반복과 별도로 미사용 표현을 시험한다. 최초 실패·관측기 오류·부분 결과를 보존하고 재시험 성공으로 덮지 않는다. 누락·오대상·근거 없는 완료/정상 주장부터 평가하며, 부분 응답이 빠른 것을 속도 우위로 인정하지 않는다. 검증된 이전 표 재서식과 정책 설명의0모델 지연은 새 조회 지연과 따로 집계한다. 실제 결과·남은 한계는 [STATUS](../../STATUS.md)를 따른다.

## 배치와 검증

초기 설치 진입점은 루트 `deploy.sh`다. SIEM 내부 설치기는 기존 문맥/훅5파일과 query 플러그인8파일을 배치한다. 후자는 `__init__.py`, `plugin.yaml`, `alignment.py`, `grounding.py`, `chat_harness.py`, `chat_contract.py`, `soc_policy.md`, `read_contract.py`이며 마지막 다섯 파일은 각각 canonical 소스를 복사한다. Ollama 내부 설치기도 같은 정책·grounding 소스를 복사하고 receipt SHA를 검사한다. 새 wheel/deb/이미지/포트는 없다. 오프라인 반입 시 기존 manifest 바이너리와 **갱신된 프로젝트 소스 전체**를 함께 반입해야 한다.

기존 운영 서버는 전체 초기 설치기로 덮지 않는다. 유휴 확인→root 복구 백업→해당 플러그인/설정과 Ollama 증분 upgrade→gateway 재시작→공통 소스 SHA·SDK 옵션·실제 채팅 확인 순서로 반영했다. Memory·SOUL 원본·자동관리 설정·기존 룰을 보존하고 timer 상태를 복원했다.

검사는 중복/역순/미연결 호출 ID, 잘못된 영수증·해시, 성공 후 실패의 제안 ID 보존, 누락 대상, 관리 CLI 제외, native8개 소스 pin·7개 alias 등록/해제와 설치 경로를 포함한다. 과거 Ollama W4 실패 기록 재생에서는 두 성공 제안과 Wazuh 실패를 모두 표시한다. 이는 새로운 실제 쓰기 성공이나 점수 상승을 증명하지 않는다. 실제 쓰기6유형 반복 채점·공격/대응 E2E·새3VM 전체 설치는 별도 후속이다.
