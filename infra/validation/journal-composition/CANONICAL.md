# 통합 후보와 초기 설치 소스의 동기화

검증용 통합 후보와 정본의 차이를 대조해 다른32파일을 같은 바이트로 맞췄다. 자원 한도 설치기는 이미 같았지만 core·history·journal·Native와 공통 소비자·스킬 일부는 달랐다. 이 상태로 새 서버를 설치하면 검증한 수집 경로와 다른 코드를 쓰게 되므로 정본을 함께 맞췄다. **운영 A/B/C에 배포한 작업은 아니다.** [변경·검증 원장](canonical-sync.json) · [현재 상태](../../../STATUS.md).

| 항목 | 결과 | 근거 범위 |
|---|---|---|
| 정본 동기화 | 기본34파일 대조 중32개 변경. 실행/스킬18·시험14 | 기존 미커밋9작업과 교집합0, 원래 바이트 보존 |

| 집중 검사 | journal·Native·history·설치116통과 | 전체 회귀와 겹치므로 합산해 고유 사례로 세지 않음 |

사용한 동결 후보는 `0f625eaa82fc247b18446446d12fd170370d2586ed64f7ada172fbfa794bdd40`이다. 수정본을 새로 조합하지 않고 이미 검증한 바이트를 복사했으며 앞선 비교·패치·원문 해시는 보존했다. `deploy.sh`가 읽는 정본에 통합 내용을 반영했지만 새 OS 전체 설치를 검증하지는 않았다.

## 무엇이 달라지는가

core·Native는 등록된 서비스의 journal을 같은 분류·기간·우선순위 조건으로 읽는다. history는 실제 수집 정책을 구분해 이전 정책의 완료 표식을 새 스캔 완료로 오인하지 않는다. 두 봇이 사용하는 소비자와 기존 스킬 절도 같은 반환 계약을 따르도록 맞췄다. 스킬2개는 실행 계약이므로 동결본을 그대로 옮겼으며 설명 문서는 별도로 윤문한다.

원본 파일·검증한 패치와 초기 실패는 Git 이전 커밋과 검증 원장에 남긴다. 기존 모델·도구 권한·승인·차단 TTL과 보안장비 룰은 바꾸지 않았다. 라이브 설치 사본은 아직 이전 상태이므로 정본만 보고 새 기능을 운영에서 쓸 수 있다고 답하지 않는다.

## 남은 적용 절차

소스·캐시·소비자를 함께 전환하는 실행기는 별도로 작성 중이다. 임시 조회 차단기를 포함한50소스 경로와 서비스·부팅 차단·독립 원복·정확 승인 범위를 고정해야 한다. 새 실행기의 모의/파일 검사를 운영 복구 성공으로 세지 않는다. 초기 설치 core3개와 SDK 스킬1개의 기존 영수증 불일치도 원본 출처를 보존한 상태로 연결해야 한다.

그 뒤 관리자231 경유 적용, 실제 새 수집·MCP·두 봇 새 채팅과 의미·누락·복구를 확인한다. 실제 새 서버 전체 설치와 공격 시험은 별도 검증이며 공격 중단 지시는 유지한다. 논문66쪽 MD/PDF/DOCX는 그대로 두고 이번 정본 동기화를 미배포 개발 근거로만 기록했다.
