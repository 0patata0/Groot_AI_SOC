# DGX·Thor 관제 추론 분산 검토안

**2026-10-31 후속 결정:** 사용자 지시로 향후 기본 배치는 **DGX Spark에서 학습 → 검증한 가중치를 Thor에 적재해 추론**으로 변경했다. [현재 실행 계획](../../finetuning/DGX_TRAINING_THOR_INFERENCE.md). DGX SSH 접속이 추가됐지만 새 학습·가중치 이동·운영 모델 전환은 아직 없다. B의 두 에이전트와 현재 Thor 연결을 유지한다.

아래 내용은 같은 날 앞서 검토한 **미구현·미전환 대안**으로 보존한다. 당시 DGX는 일반 모델 API, 학습본은 Thor에서만 사용한다는 제약에 맞춘 안이었다. 이후 학습 환경을 옮긴다는 현재 결정과 혼동하지 않는다. DGX 일반 모델로의 봇 분산은 현재 기본 실행 계획에서 제외하고, 추후 별도 요청·비교가 있을 때 재검토한다. 최신 완료·품질 합격·운영 승격은 [STATUS](../../STATUS.md)를 기준으로 한다.

## 이전 추론 분산 후보 (이력)

에이전트 프로그램·채팅·사건 담당 배정은 B에 유지하고 기존 A/B MCP·승인 실행 경계를 공통 사용한다. Hermes→Thor, Ollama 봇→DGX를 기본 연결 후보로 하되 두 에이전트 모두 조사·판단·조치안 작성·승인 요청·적용 후 확인을 수행하는 관제원이다. 단순 보조 응답 역할로 제한하지 않는다.

| 요청 | 우선 배정 후보 |
| --- | --- |
| 직접 `@hermes` / `@ollama` | 지정 봇의 추론 서버 |
| 공동 채널의 짧은 조회 | 검증된 처리 여유가 있는 쪽. 일반 모델의 MCP 조회도 완료 답변 가능 |
| 복잡한 사건·위험 판단·대응안 | 품질 검증을 통과한 Thor 학습본 우선 |
| 정기점검·후속 조사·보고 | DGX 우선. 사용자·긴급 요청보다 낮은 실행 우선순위 |
| 중요한 변경·불확실 사건 | 한쪽이 책임 조사, 다른 쪽이 독립 재조회·검증 |
| 대량 자료 | 필요할 때만 코드 기반 선별·집계, 선택적 모델 정리 |

모든 요청을 Thor가 먼저 분류하거나, 양쪽이 항상 회의하거나, Thor가 매번 정제한 뒤 DGX가 답하는 기본 경로는 채택하지 않는다. 요청별 분산은 동시 작업의 대기를 줄이는 후보이며 질문 하나의 생성시간 단축을 보장하지 않는다. DGX는 공유 서버이므로 자체 요청 수만으로 전체 GPU 혼잡도를 안다고 표시하지 않는다. API 성공/지연·B의 대기열을 관찰하되 모델 적재 여부를 전체 동시 처리 여력으로 오해하지 않는다. [Ollama 병렬 처리·메모리·대기열](https://docs.ollama.com/faq) · [적재 모델 API](https://docs.ollama.com/api/ps).

## 관제 책임과 정보 보존

- 사건 ID마다 실행 담당 하나, 승인·후보 해시·실행/검증 상태를 공통 저장한다. 검토자는 독립 읽기로 의견을 남기며 같은 조치를 중복 실행하지 않는다.
- 모델이 바뀌어도 MCP의 승인·보호 주소·TTL·증거·중복 실행 방지 검사는 유지한다. 응답 시간 초과 후 다른 모델로 보호 호출을 재생하지 않는다. 먼저 실행 상태를 확인한다.
- 학습본과 일반 모델은 답변 일치가 아니라 실제 근거·누락·대상·권한·시간 정확도로 평가한다. 모델 간 이견을 단순 다수결로 덮지 않는다. 중요 변경의 미해결 이견은 승인 전 명시한다.
- 정제 시 원본 사건 ID·출처·시각·조회 범위·전체/반환 수·생략/잘림을 보존하고 MCP로 원자료를 다시 읽을 수 있게 한다. 요약은 원본 증거·관리자 승인·전체 조회 증명이 아니다. 기존 Vector 정제를 불필요하게 반복하지 않는다.
- Thor 학습본에도 실행 통제와 근거 검증 하네스는 유지한다. 현재 Native 어댑터의 모델명 검사는 `qwen3.6:35b`에 고정돼 있으므로 학습본 승격 전에 정확한 모델 프로필과 해당 어댑터 적용을 함께 검증해야 한다.

## 전환 전 검사와 복구

1. B에서 두 API 접속·모델 이름/manifest/양자화/템플릿·지원 옵션 대조. 같은 이름이어도 동일 모델 구성이라고 추정하지 않는다. SSH는 DGX 사용의 필수 요건이 아니다.
2. 모델·하네스·자료·요청/근거 해시를 기록하고 새 스레드의 짧은 조회·사건 판단·쓰기 승인·누락 검사를 수행한다. 현재 학습본은 별도 품질 합격 후 투입한다.
3. 현재 단일 경로와 요청 분산, 필요하면 대량 자료의 정제 경로를 비교한다. 동일 하네스를 먼저 유지하여 모델/배치 변경과 하네스 축소 효과를 섞지 않는다.
4. 채팅 게시→최종 답변 p50/p95, 모델 적재/입력 처리/생성 시간, MCP 시간, 오류/부분 조회·중요 근거 누락률을 함께 비교한다. 단순 HTTP 응답시간을 모델 생성 성능으로 표시하지 않는다. [Ollama chat 응답의 시간·토큰 통계](https://docs.ollama.com/api/chat).
5. 단계적 전환과 기존 endpoint/config 복구본, 사건 담당 고정·진행 중 보호 호출의 전환 금지, 장애 시 미확인 처리부터 구현한다. 새 설치기는 기존 단일 `deploy.sh`와 함께 갱신한다.

12:46 KST B에서 읽기 전용으로 DGX 현행 API와 현재 Thor 연결 API의 tags/ps를 확인했다. 두 곳에 `qwen3.6:35b`가 있지만 manifest digest가 달랐고, 당시 DGX의 적재 목록은 비어 있으며 Thor에는 해당 모델이 적재돼 있었다. 이전 DGX 주소는 접속 실패였다. 이는 그 시점의 접속·목록 관측이며 속도·품질 비교가 아니다. 신규 생성 시험·가중치 이동·자동 분배·endpoint 변경은 이 검토에서 수행하지 않았다.
