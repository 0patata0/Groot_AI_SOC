# 서비스 조회의 대상·기간·출력 계약

서비스 상태를 물었는데 Wazuh 에이전트 목록을 답하는 문제와, 수집 관측 시각을 실행 시각으로 바꾸는 문제를 보완했다. 기존 MCP와 추론 모델을 사용하며 서버·도구·쓰기 권한을 추가하지 않는다. 실제 적용·새 채팅 결과와 미완료 범위는 별도 검증 원장을 따른다.

## 대상과 읽기 범위

| 질문 예시 | 실제 등록 대상 | 필요한 읽기 |
|---|---|---|
| A 서버 인증서 감시 서비스 현재 상태와 최근 실행 결과 보여줘 | a:certificate-monitor | 현재 수집 속성 + 해당 unit의 journal 표본 |
| A 서버 저장소 감시 서비스 현재 상태와 마지막 실행 결과 알려줘 | a:storage-monitor | 같은 절차, 다른 등록 unit |
| B 서버 도커 현재 상태와 직전 실행 기록 보여줘 | b:docker | B의 등록 unit과 지정 구간 |
| C 서버 apache2.service 현재 상태와 최근 실행 결과 보여줘 | c:apache | C의 등록 unit과 지정 구간 |
| 서비스 서버 에이전트 ID와 현재 연결 상태 보여줘 | Wazuh의 해당 호스트 에이전트 | 서비스 unit 조회와 구분한 ID·연결 조회 |

표의 서비스 이름은 응답을 외운 분기 조건이 아니다. 실제 get_system_diagnostics 스키마의 target, unit 매핑, 표시 이름과 호스트를 대조한다. 현재 상태 조회로 이력 읽기를 대신하지 않으며 요청하지 않은 에이전트 조회를 서비스 결과로 사용하지 않는다. 대상이 등록돼 있다는 사실도 실제 조회 성공과는 다르다.

기간 없는 최근·마지막 실행 결과는 실제 스키마에 등록된 기본 최근 표본으로 시작한다. 초기 표본 구간을 표시하고 그 이전 이력은 미확인으로 남긴다. 현재 수집 속성의 마지막 종료값과 journal의 시각·내용을 구분한다. observed_at_kst는 수집 관측 시각이며 실행 시각으로 바꾸지 않는다. 지정 구간과 오류 필터는 기본값으로 대체하지 않는다.

## 두 실행 경로의 공통 절차

1. 두 경로의 전송용 사용자 표시를 공통 query_body에서 분리한 뒤 서비스·호스트·기간을 실제 카탈로그로 해석한다. 숫자가 포함된 사용자 이름을 조회 기간으로 읽지 않는다. 원 요청의 감사·권한 근거는 보존한다. 기존 읽기 권한 안에서 필수 호출을 만든다.
2. Native에서는 현재 제공된 도구와 원본 레지스트리를 대조한다. 원본 조건은 전송 단계가 최상위 조건만 제거했고 다른 내용이 정확히 같은 경우에만 계획에 사용한다. 도구 누락·정의 변화·레지스트리 불일치는 복원하지 않는다.
3. 모델은 검증한 필수 읽기 목록에서 index를 선택한다. 인자를 다시 생성하지 않으며 누락·중복·범위 밖 선택은 실행 전에 거절한다. 실행은 기존 Native 또는 SDK 실행기가 담당한다.
4. 실제 응답의 대상·기간·원문 SHA·신선도·읽기 성공 여부를 검증한다. 실패·오래된 응답·표본 0건으로 정상이나 전체 이력 부재를 판단하지 않는다.
5. 단순 사실 조회는 기존 사실 조회 스키마로 범위를 확인하고 실제 반환값에서 표를 만든다. 원인·영향·정상 판단·복구·누락 없는 전체 요청은 이 사실 표시로 대체하지 않는다. 스킬의 지시로 권한·보호 정책을 바꾸지 않는다.
6. 단순 사실 조회가 실제 카탈로그와 신선한 완전한 응답으로 결속됐다면 과거 정적 별칭 검사로 다시 거절하지 않는다. 근거·권한·주장 검사를 먼저 적용하며 원인·영향 조사에는 기존 검사를 유지한다. 초기 표본 안내는 마지막 제어 레코드 앞에 두고, 공개 채팅에서 내부 상태 문자열이 제거되는지 확인한다.

저장소에서는 query-completion 디렉터리의 test_service_catalog_phase와 ollama-trial 디렉터리의 test_service_identity_scope를 python3 -B -m unittest로 실행한다. 기존 개발 환경의 jsonschema를 사용하며 Mac에 새 패키지를 설치하지 않는다. 운영 후보 검사는 실제 설치본 복제와 현재 카탈로그를 사용한다. 새 서버 설치는 기존 단일 deploy.sh가 같은 공통 파일을 복사하고 영수증 SHA를 만든다. 새 패키지·포트·키·별도 설치 진입점은 없다.

운영 반영은 관리자231 경유로 수행한다. 원본·후보 SHA와 파일 소유권·모드·보호 파일·작업 중인 사건/대기열을 대조하고 독립 원복 타이머를 둔다. 관련 봇의 새 실제 채팅과 실제 호출을 확인한 뒤 확정한다. 과거 후보의 실패·원복을 마지막 성공으로 덮어쓰지 않는다.

등록되지 않거나 대상이 모호한 요청을 현재 관측 완료로 처리하지 않는다. 명확한 등록 서비스의 현재 사실 조회와, 복합 원인·영향·전체 이력 조사·모든 새 표현의 처리·일반 정확도/SLO·새 OS 전체 설치는 별도 검증 범위다.

6개 새 대화에서 실제 읽기 10회를 대조했다. 인증서 journal은 초기 구간 0행, 저장소 journal은 5행이며 현재 종료값 0과 구분해 표시했다. 에이전트 질문은 실제 groot-web의 ID 002·ACTIVE로 답했다. 공개 표의 대상·기간·시각·표본 수와 내부 상태 레코드 제거를 확인했다. 단회 표본이며 일반 정확도나 응답시간 SLO는 아니다. 두 클라이언트의 모든 브라우저 화면을 검수하지 않았다.

동일 동결 후보의 Mac 795검사와 Linux 795검사·공식 Harness² 38검사·설치 37검사를 통과했다. 서로 겹치는 실행 횟수이며 독립된 정답 사례 수로 합산하지 않는다. 실제 운영 Harness²는 전후 passed, 카탈로그 45도구·42진단 대상, balanced 모델과 hermes-parity를 유지했다. 두 경로의 상시 지시 문자 수는 증가하지 않았다.

운영에는 소스 13개와 SDK 영수증 1개를 반영하고 보호 파일 58개를 대조했다. 같은 Native 컨테이너를 계획에 따라 1회 재시작하고 SDK·교차 검토 작업자를 갱신했다. 작업자 정지 구간의 DB 바이트가 같음을 확인했으며 작업을 삭제하지 않았다. 실제 채팅 검수 후 독립 원복 타이머를 해제했다. 원본·정확 후보·제어기는 운영 복구 위치에 보존한다.

패치는 당시 설치 원본에 대한 재현 자료다. 현재 정본이나 다른 서버에 무조건 적용하는 설치기가 아니며 영수증·승인·보호 검사를 대신하지 않는다. 실제 검증에서는 13개 원본 복제에 패치를 적용하고 역적용해 양쪽 SHA를 대조했다. 신규 설치는 기존 deploy.sh를 사용한다. 실제 새 OS 전체 설치는 하지 않았다.

실패한 이전 후보는 각각 원복했고 준비만 한 후보는 운영 적용으로 세지 않았다. 모델의 인자 생성 오류, 자유 서술의 기능 정상·실행 시각 오판, 전송 라벨 처리 누락, 공개 상태 문자열 노출과 정적 별칭의 중복 거절을 별도 원인으로 기록했다. 최종 사실 조회의 성공을 복합 원인 판단 해결로 확대하지 않는다. 하루 전체 이력 질문 2개는 보류했으며 통과로 집계하지 않았다.

현재 상태만 요청하면 과거 조회 구간을 만들지 않는다. history_window_origin은 current_observation_only, history_windows는 빈 목록이며 초기15분 안내도 붙이지 않는다. 실제 카탈로그에 연결한 현재 관측과 마지막 종료 속성을 표시하고 기능 전체의 정상이나 사건 종결로 확대하지 않는다. 원인·영향·전체 이력·재조회·비교·설정 변경 요청을 현재 스냅샷으로 대신하지 않는다.

도구 목록을 좁히기 전에 요청의 객체 종류를 구분한다. 명시적인 에이전트 질문과 단순 ID·연결 상태는 유지하지만 호스트 옆에 미인식 객체명이 남으면 에이전트 ID 조회로 단정하지 않는다. 이 공통 제한은 저장소 이름 한 개의 예외가 아니다. 새 등록 표시 이름을 바꾼 반례와 한국어 조사 뒤의 ID, 기존 교차 검토를 함께 검사했다.

같은 사용자·같은 대화에서 “C 서버”라고 답하면 바로 앞 요청의 서비스와 조회 조건을 유지하고 호스트를 바꾼다. 어댑터가 확인한 사용자 요청만 사용하며 새로운 주제·쓰기·검증하지 않은 이력을 이어받지 않는다. 이전 도구 응답의 수치나 승인은 사용하지 않고 새 호출과 반환 SHA를 검증한다. 위8요청은 새 대화6개와 후속2개이며 같은 대화 전체의 누적 도구 수를 각 요청의 실행 수로 세지 않았다.

처음 적용한 후보는 SDK가 저장소 질문을 에이전트로 축소해 잘못 답했으므로 확정하지 않고 원복했다. 해당 오류와 이후 ID 조사 경계의 회귀 실패는 검증 원장에 남겼다. 최종 후보는Mac830검사, Linux830검사·공식38검사·설치37검사와 실제8요청의6읽기를 통과했다. 운영10소스·영수증1개/보호61파일, 같은 Native 컨테이너의 계획 재시작1회와 작업자 정지 중 DB 바이트 일치를 확인했다. 독립 원복 타이머는 확인 후 해제하고 원본·후보·제어기를 보존했다.

운영 최소 패치는 이번 설치 원본10개를 기준으로 갱신했다. 실제 서버에 재생한 패치가 아니며 격리 원본 복제에서 적용·역적용 SHA를 검증했다. 이전13파일 패치와 검증 원장은 내용 커밋8ec5946의 같은 경로에서 복구한다. 정본의 전체 모듈과 운영의 필요한 함수만 반영한 사본을 구분한다. 새 서버는 기존 deploy.sh를 사용하며 이번에 새 OS 전체 설치를 수행하지 않았다.

## 복합 원인 조사에서 추가로 확인한 범위

두 전용 채널의 새 대화에 같은 질문을 보냈다. 질문은 “A 서버 인증서 감시 왜 실패했어? 지금은 어때?”이며 설정 변경·공격·학습 요청은 포함하지 않았다. 관리자231 경유로 설치 소스64개, 기존 확정11파일·보호61파일, balanced 모델·hermes-parity와 실제 카탈로그 SHA를 먼저 대조했다. 공식 Harness²의 새 운영 점검도 passed였다.
