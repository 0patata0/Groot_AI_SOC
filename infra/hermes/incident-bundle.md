# 복합 사건 읽기 연결·지연 검증 — 2026-11-06

두 봇과 root 사건 검증기에 [관련 MCP 읽기 묶음](../mcp/incident-evidence.md)을 연결했다. **정확한 최종 보고30초는 아직 달성하지 못했다.** [현재 상태](../../STATUS.md)와 [수치 원장](incident-bundle.validation.json)을 따른다.

## 변경한 동작

LLM이 정확한 사건/후속 구간·대상을 선택하면 기존 읽기 권한 안에서 센서, 명시한 서비스 진단, 실제 WAF 경로와 등록 agent에 연결된 웹·호스트 자료를 함께 조회한다. 모델이 조회 결과를 받은 다음 위험과 후속 조치를 판단하며, 필요한 추가 조회도 선택할 수 있다.

| 경계 | 실제 동작 |
|---|---|
| wire와 내부 읽기 | MCP 호출1회와 내부 읽기N개를 별도 집계. 내부 읽기를 독립 wire 호출로 꾸미지 않는다 |
| 근거 결속 | 실제 호출 인자·센서/시간/출발지·구성상 대상/agent·하위 응답SHA·오류를 대조한다 |
| 인용·종결 | 실제 호출한 묶음 이름을 인용한다. 별도로 읽은 다른 자료를 묶음 안에서 읽었다고 주장할 수 없다. 상태 조회만으로 침해 해소를 판단하지 않는다 |
| 실패 | 위조/누락된 구성 조회는 근거로 채택하지 않는다. 일부 오류를0건/정상으로 바꾸지 않고, 기존 개별 조회 선택을 유지한다 |
| 모델 입력 | 큰 웹 결과는 기존 무손실 열 형식으로 표시한다. 원본 감사·SHA·검증 사실은 원본을 사용하며 모든 행/필드/순서/타입/오류를 보존한다 |
| 초기화·권한 | 기존 Native/SDK 실행·연결 풀을 사용한다. 모델/키/포트/일반sudo/Docker/승인/차단TTL 변경0 |

SDK와 Native 공용 하네스는 검증된 내부 읽기만 사실·대상 선택·완료 검사에 활용한다. 원래 wire 감사와 도구 호출 예산은 그대로다. 묶음 실패/비정상 결과를 새로운 성공 조회로 대체하지 않는다.

root 실행 gate의 인자 포장은 LZMA+base85로 바꾸고 원본SHA와 포함코드의 일치를 검사한다. 실제 인자64,565B로 Linux의65,536B 단일 인자 한도 안이다. 포함코드만 바꾸거나 오래된 참조파일을 허용하지 않는다.

## 검사와 실제 시간의 구분

- 최종 고유1,215검사: management439, SDK231, Native query391, 설치41, 표19, 공통 출력7, MCP 묶음19/이벤트30/진단38. B venv에서 Native 의존57개를 skip한 것은 실제 Hermes 환경439개/skip0 검사로 보완했다.
- SDK 운영 계정·기존 연결 풀: 실제 wire1/내부8조회2.591초, 근거16개·오류/모델/게시/쓰기0. 이는 최종 모델 보고 시간이 아니다.
- 첫 query1.19.73 실제 복합 조사: 새 세션42.973초, 모델2회28.431초, wire2회(상태1+묶음1), 내부8조회. 실제 근거 표/인용 일치·오류/쓰기0, 침해 영향은 미확인으로 유지했다. 표현 명확성과 구체적 후속 계획의 품질까지 완벽하다는 의미는 아니다.
- 다른 IDS 사건의73 시험은166.999초/모델5회/실제wire8회로 느렸다. 추가 조회와 큰 웹 결과의 반복 입력이 확인됐고, 운영자 지시 대기로 끝낸 후속 계획도 미흡했다. 이 결과를 성공적인30초 보고로 집계하지 않는다.
- 74는 묶음 안의 웹 로그에도 기존 무손실 표시를 적용한다. 같은 IDS 영수증46,112→27,984B, 원본은 그대로다. 새 IDS 재측정은68.880초/실제wire2·내부7조회/모델3회였지만, 최종 판단 검증을 통과하지 못해 사실표와 검토 필요 안내로 끝났다. **유효한 최종 보고 완료가 아니다.** 최초 보고28.778초 뒤 정정22.825초가 추가됐다. Vector 서비스 표현을 웹 상태 주장으로 잡는 과도한 검사 범위와 별개로, 근거 없는SNI/정책ID 계획·후속IDS0표본을 재탐지로 묶은 모델 오류도 확인됐다. 검사를 풀어서 성공으로 바꾸지 않았다.

추가 비공개 모델 비교에서는 규격을 나중에 제공하는 안이17.599초 뒤 추가 근거를 요청했고, 관련 도구 우선 제공안도21.550초 뒤 추가 조회를 선택했다. 두 안은 최종 보고 단축을 증명하지 못해 운영에 넣지 않았다. 추가로 생성 규격만 단순화하고 실제 호출 전 전체 규격 검증을 유지한 후보도27.631초/27,482입력토큰 뒤 차단 목록 추가 조회를 선택해 비채택했다. 이들 후보는 보존한 영수증의 모델 재생이며 신규 실제 조사가 아니다. 읽기 선택권이나 필요한 근거를 없애서30초를 맞추지 않는다.

전체 조사 시험3건은 실제 읽기·실제 모델을 사용하는 비공개 새 세션이며, 운영 사건 DB를 복사한 시험 DB에만 기록했다. Mattermost 게시·큐 전달·UI 시간과 실제 공격 E2E는 이번 수치에 포함하지 않는다. 공유 모델 부하를 통제한 반복 평균/SLA도 아니다.

## 운영·설치·복구

query1.19.74/common1.5.33·security-events1.3.0/진단1.2.2를 관리자231 경유로 반영했다. 소스16개와 SDK receipt를 동기화하고 양봇WS/worker·4서비스·보호설정7SHA·root 포함코드를 확인했다. MCP는 실제 비권한 wrapper에서 읽기7개를 광고한다.

단일 초기 진입점은 `deploy.sh`이며 기존 SIEM/SDK/사건관리 source 복사와 `incident_evidence.py` 설치를 사용한다. 내부 MCP 설치 검증도7읽기로 맞췄다. 새 패키지/이미지/입력 설정은 없다. 운영에 초기 설치기를 실행하지 않았고 새 OS 전체 설치 시험도 하지 않았다.

B의 `/var/lib/capstone-bundle-integration/20261106-r1/deployment`는72→73, `20261106-r2/deployment`는73→74 백업/정확 manifest/원복 스크립트를 보존한다. 각각15분 독립 원복을 준비하고 상태 검증 후 확정했다. 확정 후 자동 원복 no-op은 확인했지만 실제 수동 원복은 실행하지 않았다. 되돌릴 때는 활성 작업이 없는지 확인하고 정확 manifest의 현재SHA를 확인한다. 이전 후보로 되돌리거나 여러 단계 원복하는 순서를 혼동하지 않는다.

후속 [16개 재생 비교](incident-review-probes.md)는 별도 단위이며 신규 운영 변경은 없었다.

정리·Git 게시 상태는 수치 원장과STATUS에 구분한다. 운영 DB·trace·복구본·모델은 정리 대상이 아니다.
