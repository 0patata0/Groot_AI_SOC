공통71/원본35B에서 원문·현재 상태를 실제로 읽고도 검토 사건 수를 처리 지연으로 바꾸는 문제가 남았다. 실제 두 채팅의 첫4조회를 각각 동결해 입력 배치와 출력 구조 후보를 비교했다. **후보는 모두 운영 비채택**이다. [검증 원장](service-report-layout.validation.json) · [운영 원문 조회와 실제 채팅](../mcp/journal-excerpts.md).

## 조건과 범위

- 입력은 같은 질문·사건에 대한 Hermes/Ollama 두 관측 묶음이다. 각4조회·원문32행/고정 오류8행을 포함한다. Hermes 묶음의 현재 oneshot은 inactive/dead·성공 종료, Ollama 묶음은 activating/start다. 검토287건과 처리/실행/기한 초과0건은 각각의 원자료와 대조했다.
- **모든 생성은 기존 B SDK의 ChatOllama로 실행했다.** 표의 H/O는 자료 출처이며 Hermes Native와 SDK 런타임을 비교한 수치가 아니다. 원본 qwen3.6:35b·temperature0/top_p0.95/추론off/출력2048을 유지했다.
- 실행 전 실제 읽기 도구35개와 운영 source SHA를 확인했다. 도구 목록만 조회했으며 신규 진단 MCP 실행·보호 작업·채팅 게시0이다. 실제 조사/대응 E2E나 미사용 독립 평가로 세지 않는다.
- 질문·원문·서버 속성을 모델 정답으로 바꾸지 않았다. 이전 초안·정답은 초기 비교 입력에 넣지 않았고 학습에도 편입하지 않았다.

## 실패와 다음 변경 조건

첫2개 후속 인자 시험은 생성·스키마 검증 후 분석 코드가 잘못된 모듈의 alias를 호출해 AttributeError를 냈다. 생성 JSON·실제 인자는 보존했고 원자료의 tool/arguments와 로컬에서 다시 대조해 동일 조회임을 확인했다. 모델을 재생해 결과를 바꾸지 않았고 서버 오류로 표시하지 않는다. 준비만 하고 실행하지 않은 다른 후보는12개에 포함하지 않는다.

원문 조회·하네스 common71/query122·SDK 상태 수정은 유지한다. 이번 입력/스키마 후보는 배포·재시작0이다. 단순 분기 순서만 원인으로 볼 근거는 없고, 입력 배치는 답변 선택에 영향을 줬으나 정확도 개선은 확인되지 않았다. `case_review_required`를 포함한 수집기의 종합 degraded와 실제 처리 지표·사건 검토 상태의 구분을 다시 점검하고, 각 판단을 해당 관측 필드에 연결해야 한다. Native/SDK의 반복 조회 제어도 같은 기준으로 맞춰야 한다. 이는 다음 검증 가설이며 해결 완료가 아니다.

후속 후보는 다른 표현·사건 및 실제 처리 지표가 양수인 반례에서도 검증한다. 근거 부족은 숨기지 않되 확보한 원문이나0건 지표를 미조회로 바꾸지 않아야 한다. 필요한 추가 읽기는 실제 실행하고, 똑같은 조회를 반복하며 끝내지 않도록 개선한다. 정확한 새 채팅·승인/쓰기 경계·회귀 검증 전에 운영 채택하지 않는다.

실행 소스는 관리자 경유로 기존 비특권 SDK 환경의 메모리에만 전달했다. 서버 반입 파일·Mac 신규 패키지/다운로드0이며 로컬 검증 소스/원문은 Git 제외 증거로 보존한다. DGX 현황 조회·학습 변경·모델 승격·공격 재생은 하지 않았다.
