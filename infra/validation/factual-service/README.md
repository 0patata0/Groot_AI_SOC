# 사실 조회의 범위와 미확인 표시

**일부 개선을 실제 SDK로 확인했으나 의미 오류가 남아 운영 승격하지 않은 후보**다. [부모 타입/실행 후보](../typed-service/README.md)도 미적용이다. 현재 설치 소스를 이 후보로 설명하지 않는다.

| 무엇을 바꿨나 | 어떻게 바꿨나 | 이유 |
|---|---|---|
| 단순 상태·기간 로그 조회 | 실제 스키마에서 해석한 이름·동일 파서의 기간을 재사용. 나머지 문장은 닫힌 조회 범위와 대조 | Docker 같은 표시 이름과 ‘최근 N분’ 때문에 원인 조사로 확대되던 흐름 수정 |
| 로그 요청의 조사 | ‘로그에서·로그에도·로그로부터’의 명사 조사를 시간 구간과 분리 | ‘실제 로그에서 오류 원인’이 원문 대신 색인만 읽던 결함 수정 |
| 미확인 요약 | 응답 수신·unit loaded/not-found·논리 구성요소 식별을 분리 | 목록을 읽었다고 구성요소 식별까지 확인한 것처럼 표시하지 않음 |
| 근거 경계 | 기존 두 공통 스킬 재사용·물리 파일 주장 검사 | unit 검색과 전체 파일·프로세스 존재를 구분. 새 구문 검사에도 잔여 오탐이 있음 |

## 실제 응답 대조

R1은 부모 query147/common91과 초기 후보148/92를 같은 모델·권한으로 순서대로 실행했다. 같은 질문을 사용했지만 공유 GPU·캐시·로그 구간·순서는 통제하지 않았다.

| R1 같은 요청 | 부모 시간/결과 | 초기 후보 시간/결과 |
|---|---|---|
| B Docker 현재+최근3분 로그 | 24.210초·partial | 14.448초·조회 완료 |
| B systemd 최근7분 로그 | 29.236초·partial | 23.178초·조회 완료 |

R1의 ‘로그에서 오류 원인’은 cached history만 읽었다. 이 실제 실패를 고친 최종 R2는 별도 소스 해시로 동결하고 다시 검사했다. R1 결과를 R2 결과로 바꾸지 않는다.

R1 부모2/후보4와 R2 후보4, 총10회 실행·서로 다른 질문 문자열7개·SDK23읽기·기록된 모델 완료23회다. 별도 wire smoke4읽기와 초기 운영 MCP3읽기를 구분한다. 모든 실행은 새 대화 입력이며 실제 서버의 등록된 읽기를 사용했다. Mattermost 왕복·실제 Hermes 추론·독립 SOC 정확도·학습 모델 우위의 근거가 아니다. 실행기의 completed는 요청 실행 완료이고 전체 품질 합격이 아니다.

## 아직 통과하지 못한 부분

| 문제 | 확인한 근거 | 다음 보완 |
|---|---|---|
| unit 속성을 실제 프로세스로 설명 | R2 Vector가 not-found 뒤 ‘현재 프로세스 실행 상태는 inactive/dead’라고 씀. 기존 실행 검사가 놓침 | 단순 조회의 미확인 응답도 타입·범위가 결속된 형식으로 제한 |
| 확인하지 않은 구성요소 관계 | Vector 식별이 미확인인데 실제 목록의 일부 컨테이너를 ‘관련 컨테이너’로 묶음 | 목록 관측과 실제 서비스 매핑을 구분 |
| 실제 인용과 새 주장 혼동 | 구성한 source-quote 반례에서 새 파일 주장 검사가 인용까지 거절 | 인증된 원문 표시와 모델 주장을 분리. 임의 표 전체를 면제하지 않음 |
| 불필요한 출력·입력 | 현재 상태만 물어도 기본15분 부가 표본을 표시. R2 호스트 조회 합성 입력16,374토큰/출력72토큰 | 질문 필드와 검증된 조회 범위 요약 중심으로 줄이기 |
