## 왜 통합했는가

앱이 `level=error`로 쓴 기록도 journal 우선순위는 info일 수 있다. 이전 고정 문자열 검색에서는 실제4건이 오류 발췌와 보관 색인에서 빠졌다. 반대로 구조화된 정상 로그까지 전처리 후보로 읽으면 CLI의 제한된 tail을 채울 수 있다. 따라서 파서의 분류, 시간 구간, Native의 선택 순서, 캐시의 수집 정책, 봇의 표본 해석을 함께 대조해야 한다.

기존 후보의 마이크로초 시각 검증을 보존하면서 앱 수집 정책을 합쳤다. MCP 후보 버전은1.4.6이다. `get_system_diagnostics`의 기존 호스트 대상에 **명시적인 `view=journal`일 때만** 시스템 journal을 허용한다. 사용자 journal과 개별 서비스 오류 색인을 혼동하지 않는다. 도구 수3개와 포트·OS 계정 권한·쓰기 승인 경계는 유지한다. 입력 스키마의 조건부 허용 범위는 실제로 달라졌으며, [차이](validation.json)에 기록한다.

## 공통 처리와 장비별 범위

새 앱 분류는 최상위 JSON/logfmt의 `level`·`severity`·`log.level`을 한정해 읽는다. 메시지16,384문자·필드64개 이내에서 중복·충돌·잘못된 타입을 거절한다. 본문/중첩 객체·HTTP 코드만으로 앱 오류를 생성하지 않는다. 기존 우선순위0..3 기록의 분류는 유지하고, 새 `application_error`는 우선순위4..6에서만 허용한다.

공통 소비자는 실제 요청 구간에 속하는 시각과 유효한 수준·형식만 표시한다. 현재 수집 표본의 Unix 시각은 KST로 표시하되 존재하지 않는 커서 해시를 만들지 않는다. 과거 색인의 원문 ID와 현재 수집 표본을 다른 출처로 유지한다. `application_error`만으로 공격·손실·원인·현재 영향·복구를 확정하지 않도록 기존 `soc-investigate` 절을 보완했다.

보관 색인의 `source_filter_policy=application-severity-v1`과 현재 정책의 실제 구간 스캔을 확인한다. 이전·다른·미보고 정책의 완료 표식은 현 정책의 완료 근거가 아니다. 첫 새 정책 게시의 표식 초기화·기존 이벤트 보존·실패 롤백은 격리 DB에서 검증했다. **실제 운영 DB의 게시·재스캔은 하지 않았다.** 실제 기존 캐시는 같은 과거 구간에서0건·legacy-unversioned·부분 미확인으로 반환됐다.

스킬 전체가24KiB 로딩 한도를 넘는 문제도 실제 호출로 발견했다. 한도를 늘리지 않고 호스트 범위의 중복 설명을 압축해24,456바이트로 맞췄다. 일반 역할·승인 원칙을 바꾸거나 새 스킬을 복제하지 않았다.

## 고정 소스 재현

Python3.12와 보존된 공식 `G_Harness2/`가 필요하다. 기존 패키지를 사용하며 새 환경·모델·자격 파일을 내려받지 않는다. 출력 경로는 저장소 밖의 아직 없는 경로로 고른다.

```sh
python3 -B infra/validation/journal-composition/reproduce.py --repo . --output /private/tmp/soc-journal-replay
python3 -B infra/validation/journal-composition/run_regressions.py --root /private/tmp/soc-journal-replay/candidate --comparison /private/tmp/soc-journal-replay/comparison-base --environment mac --output /private/tmp/soc-journal-checks
```

재현기는 전체 기준2,266파일에서 후보2,271파일과 비교용3소스를 복원하고 SHA·공식 구조를 검사한다. 과거 후보를 반복해서 중첩 복사할 필요가 없다. 회귀기는 후보의 전체 트리, 고정 시험 입력, 프로필별 실행 수를 확인하고 Python socket 연결을 거절한다. 모델·MCP·실제 journal·배포를 호출하는 실행기가 아니다.

기존 Hermes 의존성이 있는 시험 환경에서는 `--environment hermes`로 공통 서비스 시험147개를 포함해 실행한다. 이 모드의 생략은 허용하지 않는다. Mac 모드에서는 관측된 root 프로필의 의존성 생략6개까지만 허용한다. 새로운 패키지를 Mac에 설치해 결과를 맞추지 않는다. 프로필별 명령과 수는 [회귀 목록](regressions.json)에 고정했다.

실패하면 출력 디렉터리의 해당 stdout/stderr와 `results.json`을 확인한다. 소스/시험의 SHA 불일치나 미완료·예상 밖 생략은 통과가 아니다. 원문과 기존 복구본을 보존한 뒤 새 후보로 다시 검증한다.

## 실제 읽기와 남은 배포 조건

실제 Native 부모 실행은 root 소유·비쓰기 상위 경로를 요구한다. 일반 Hermes 데이터 경로의 시험 사본은 이 보호 검사에서 거절됐다. 검증한14소스를 별도 root 전용 임시 경로에 두어 부모/작업자 경로까지 확인했고, 점검 뒤 임시 경로는 제거했다. 이 경로를 운영 설치나 에이전트의 일반 root 권한으로 남기지 않았다.

## 소스 대조와 캐시 복구 준비

무엇을: 설치된 코드·실제 import 경로·무결성 영수증을 대조해 [대상 목록 초안](release_inventory.json)을 만들었다. A4+B32+C4의40경로이며 B는 코드30개와 기존 영수증2개다. 이미 일치하는 교차 채널 코드는 보존하고, 실제로 없는 선택적 별칭9개는 생성 대상에서 제외했다. 부재를 곧바로 설치 누락으로 처리하지 않았다.

왜: 소스만 되돌리고 새 정책의 스캔 표식을 남기면 이전 필터가 읽지 않은 구간을 완료로 오인할 수 있다. 반대로 캐시 전체를 무조건 덮어쓰면 변경 뒤 관측을 잃을 수 있다. [복구 모듈](cache_transaction.py)은 고정 진단 메타데이터 DB만 다루고 변경 전 바이트·논리 해시와 변경 뒤 사본을 모두 보존한다. 채팅·사건·승인·원시 journal DB는 대상이 아니다.

### 후임자가 검증을 재현하는 순서

1. [검증 원장](cache_validation.json)에서 모듈·시험 SHA와 환경별 결과를 확인한다. 소스가 달라지면 이전 통과를 재사용하지 않는다.
2. 저장소 루트에서 아래40개 격리 시험을 실행한다. 실제 경로·서비스·MCP·모델에 접근하지 않는다. 실패·생략이 있으면 적용 단계로 넘어가지 않는다.

```sh
python3 -B infra/validation/journal-composition/test_cache_transaction.py
```

3. 실제 배포 전에는 수집 타이머·실행 중 수집기·reader와 B의 코드 소비자를 함께 정지·대기시키는 조정 실행기를 먼저 완성한다. 이 모듈은 서비스를 중지하거나 배포 권한을 부여하지 않는다. `filesystem_root`는 명시적인 Python 격리 시험 인자이며 MCP·계획·환경변수·CLI 입력으로 노출하지 않는다.
4. 조정 실행기는 고정 root 경로·소유자·그룹·권한·단일 링크·SQLite 스키마·정책·무결성을 확인한 뒤 `prepare()` 결과를 검증해야 한다. WAL/SHM/rollback journal, 불명 정책, 해시 차이는 거절 사유다.
5. 원복 시에는 새 관측의 `after.sqlite3`와 영수증을 먼저 보존·검증하고 이전 바이트를 원자 교체한다. 반복 원복에서도 보존된 사본을 검증한다. 원본·변경 뒤 사본이 다르거나 손상되면 덮어쓰지 않고 멈춘다.
6. 소스/캐시 일관성·독립 복구 타이머·실제 로드·새 스캔·MCP·두 봇 새 채팅을 확인한 뒤에만 확정한다. 현재는 이 조정 실행기와 운영 인수 단계가 미완료다.

### 적용 전 해결할 문제

A·B는 구조화 로그가 CLI의 후보 행 상한을 먼저 채웠다. 캐시 준비 단계의 오류 준비0건·`history_truncated=true`는 **오류 부재나 전 구간 완료가 아니었다.** A의 운영 캐시는 과거 관측에 머물렀고 기존 필터의8초 제한도 확인했다. 아래 수집 오버레이는 의미 분류를 상한보다 먼저 적용해 격리 읽기의 잘림을 보완했다. 운영에는 아직 적용되지 않아 실제 캐시의 공백 해소를 주장하지 않는다.

Ollama 조회 스킬의 영수증1개와 진단 초기 설치 영수증3개의 core 해시가 이미 실제 파일과 달랐다. 원래 출처를 보존하고 새 배포의 영수증·검증기와 연결해야 한다. 초안의 영수증 후보를 이미 적용되었거나 새로운 전체 설치가 완료된 것으로 표시하지 않는다. 고정34소스의 공식 Harness² 구조 결과는 그대로이며, 이 독립 운영자 모듈에 공식 구조 검사를 새로 실행했다고 주장하지 않는다.

| 다음 단계 | 완료 판단에 필요한 증거 |
|---|---|
| 정확 적용안 | 40대상 초안에서 수집 잘림 보완·출처 영수증 연결·소스/캐시 조정 실행기까지 검증한 최종 payload 고정 |
| 복구 준비 | 격리 검증된 캐시 모듈에 소스·타이머/수집기·소비자의 일관된 정지/재개와 독립 원복을 연결 |
| 관리자 승인 | 새 정확 후보에 결속한 승인. 기존 관리19/journal9 계획의 승인을 재사용하지 않음 |
| 적용 후 인수 | 실제 로드·MCP 스키마·구간 조회·캐시 정책/재스캔·두 봇 새 채팅·복구 확인 |

## 수집 오버레이의 최종 검증

무엇을: 현재 snapshot과 과거 backfill이 같은 root 전용 메타데이터 수집 함수를 사용하도록 바꿨다. 기존 Native 커서 순회·등록 unit 표현식·분류/스키마 검증을 재사용한다. 우선순위별로 실제 오류로 분류된 기록을 고른 뒤 기존1,001개씩/합계2,002개 상한을 적용한다. 정상 구조화 로그 수 때문에 이전 오류가 밀리지 않는다. 상한에 닿거나 읽기가 실패하면 잘림/미확인을 유지한다.

어떻게: 고정 역할·정수 마이크로초·4시간 구간만 받는 root 전용 자식 프로토콜을 추가했다. 읽기 전후 접근 검사·최대12초 자식/16초 전체·1MiB 메타데이터 응답과 역할/unit/기간/정책/정렬/중복·그룹 상한을 검증한다. 원문 메시지·커서·경로·명령은 응답에 넣지 않는다. 기존 journal JSON의 크기/바이너리 의미와 분류 정책v1을 보존한다. 공용 MCP 인자나 권한·포트·모델·스킬은 추가하지 않았다.

|검증|최종 결과|판정 범위|
|---|---|---|
|변경|기본34소스 위 런타임3·기존 시험2의5파일 오버레이, 별도 새40회귀|기본 패치와 과거 영수증은 보존|

### 후임자가 같은 소스와 검사를 복원하는 순서

1. [오버레이 원장](collection-manifest.json)의 기본 manifest SHA·패치·5소스 SHA·추가 시험을 확인한다. 출력 경로는 아직 없는 저장소 밖 경로로 정한다.
2. 아래 재현기는 기본 통합을 복원한 뒤 전체/파일 SHA를 확인하고0문맥 패치를 적용한다. 공식 Harness² 구조 결과와 최종2,271파일의 SHA를 다시 확인한다.
3. 회귀기의 `results.json`에서 외부 종료 코드뿐 아니라 `complete`, 프로필 수, 시험 수, 생략을 확인한다. 실패·미완료는 적용으로 넘기지 않는다. Hermes 모드는 기존 의존성이 있는 환경에서만 실행하고 패키지를 Mac에 새로 설치하지 않는다.

```sh
python3 -B infra/validation/journal-composition/reproduce_collection.py --repo . --output /private/tmp/soc-journal-collection-replay
python3 -B infra/validation/journal-composition/run_collection_regressions.py --root /private/tmp/soc-journal-collection-replay/candidate --comparison /private/tmp/soc-journal-collection-replay/comparison-base --environment mac --output /private/tmp/soc-journal-collection-checks
```

실제 서버 읽기·원시 구간 대조·격리 캐시 인수·원복은 이 회귀 명령과 별도다. 원문·내보낸 DB·프로브·초기 실패 로그와 정리 영수증은 로컬 검증 원장에 보존한다. 공개 [검증](collection-validation.json)에는 필요한 결과·범위·해시만 둔다.

### 초기 실패와 운영 적용 경계

타이머 PID 필드를 가정한 사전 점검과 Docker CLI 경로를 가정한 첫 Linux 드라이버는 제품 시험 전에 실패했다. 다음 Linux 실행은944개까지 진행한 뒤 구 음성 시험1개에서 멈췄다. 이미 허용된 `b:systemd` journal을 금지로 검사하던 항목만 `b:collection`으로 정정하고, 나머지 거절 검사는 유지했다. 허용 호스트와 금지 수집 대상을 명시적으로 확인하는 양성/음성 시험을 추가해 최종40개와 전체 회귀를 재실행했다. 이전 통과를 이 계약의 증거로 재사용하지 않는다. 실제 서버를 읽은4런타임 SHA는 최종 시험 정정 전후에 같다.

기존 운영 수집기 unit은 MemoryMax=infinity였으며 runtime 수집의4개 worker 뒤 inventory 수집의5개 worker가 실행된다. 후속 [전체 수집 자원 시험](RESOURCES.md)에서는 세 서버의 전체 수집과24시간 이력을256MiB/Tasks64 제한 안에서 완료했다. 호스트별1회 관측이며 운영 unit·초기 설치기는 아직 바꾸지 않았다. 격리 읽기의128MiB/Tasks8을 전체 운영 수집기의 충분한 한도로 간주하지 않는다. 초기 설치 경로를 포함한 유한 자원 제한·소스/캐시/소비자 동시 정지·독립 원복·새 증거 결속 확정을 완성해야 한다. [현재40소스 투영](collection-release-inventory.json)은 unit/조정 범위까지 고정한 최종 승인 계획이 아니다.

이번 회귀·실제 소스 읽기를 Mattermost 응답 속도나 모델 정확도·학습 우위로 환산하지 않는다. 미선택8행의 정상 여부를 인증하거나 선택된42행을 공격42건으로 세지 않았다. Native 모듈은 운영 경로에 미설치이고 실제 reader의 PID/시작 시각, 설정과 학습 모델은 유지됐다.
