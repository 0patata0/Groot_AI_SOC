# 전체 수집기의 격리 자원 시험

A/B/C 전체 수집과 24시간 이력 수집을 격리된 자원 제한 안에서 확인했다. MemoryMax 256MiB·MemoryHigh 192MiB·태스크 상한64개에서 세 서버 모두 완료했고 OOM·태스크 한도 초과는 없었다. 운영 수집기의 제한은 아직 infinity다. 이번 결과는 관측 시점의 실행 근거이며 운영 한도의 충분성이나 최악 조건을 보장하지 않는다.

동일한2,271파일 후보를 공개 재현기로 복원해 사용했다. runtime 수집의4개 worker와 inventory 수집의5개 worker는 순서대로 실행되며 태스크에는 수집기 cgroup에 속한 subprocess와 thread도 포함된다. Docker daemon·컨테이너 안의 exec·외부 API 서버 자원은 이 제한과 측정 범위 밖이다. 기존 runtime·inventory 파일의 SHA가 세 서버 설치본과 같음을 확인했다. 시험 수집기의 게시 대상은 자체 디렉터리로 바꾸고 운영 이력 DB는 읽기 전용으로 복사했다. ProtectSystem=strict와 자체 ReadWritePaths로 파일 쓰기를 제한했다. 운영의 정기 수집은 그대로 유지했다.

각 호스트에서 한 번씩 실행한 결과다. 장애·동시 작업·최대 로그량 조건은 별도로 검증해야 한다. A/C의 이력0행은 고정 분류 범위의 결과이므로 전체 오류나 공격의 부재로 해석하지 않는다. 메모리 수치는 시험 프로세스가 읽은 cgroup memory.peak를 썼다. 종료 후 systemd 속성의 MemoryPeak와 값이 달라 원장에 따로 보존했다. 태스크는20ms 표본과 커널 pids.peak를 구분했으며 시험용 관측 thread1개를 포함한다.

초기 설치기와 운영 unit은 이번에 수정하지 않았다. 유한 한도 후보를 확정하려면 장애·최대 부하 검증과 초기 설치 경로 동기화가 더 필요하다. 그 뒤 소스·캐시·소비자의 일관 정지, 백업·독립 원복·새 증거 결속을 완성하고 정확한 관리자 승인을 받아야 한다. 기존40소스 투영과 관리19/journal9 계획의 승인은 재사용하지 않는다. 실제 MCP와 두 봇 새 채팅 검증도 남아 있다.

시험 유닛3개는 실행이 끝난 뒤 중지해 not-found를 확인했고 자체 폴더3개의36파일·3,694,595B를 정리했다. 운영 소스·설정·unit의 SHA는 사전 관측과 같았으며 운영 서비스 재시작은 없었다. 모델 생성·채팅 게시·공격·학습은 하지 않았다. 정상 수집에 필요한 읽기 전용 API 상태 확인은 포함했다.
