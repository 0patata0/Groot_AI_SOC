# 사건 보고의 반복 입력 개선과 실제 한계

2026-11-06 KST. 당시 query1.19.62/common1.5.32. 후속 현재 버전·실측은 [요청 범위 보완](request-scope.md)을 따른다. **안정적인30초 최종 보고는 아직 달성하지 못했다.** [현황](../../STATUS.md) · [수치 원장](review-payload.validation.json) · [이전 기록](automatic-review.md).

## 변경한 부분

- 단일 읽기/보고 선택을 유지하면서 전체 등록 읽기 규격·설명을 고정 접두부로 옮겼다. 바뀌는 사건 문맥·영수증·nonce는 뒤에 온다. 모델에 보이는 `$defs`와 현재 schema를 합치면 실제 API·검증기의 전체 schema와 같다. 추가 선택 단계, 도구 축소, 인자 변경은 없다.
- 웹 결과가0~1건이어도 반복되는 파일 metadata를 열과 값으로 표현한다. 모든 파일/행/필드·타입·순서·해시·잘림/범위 제한을 복원 검사하며 원문 감사/사실 표는 그대로 보존한다.
- 실제 재측정에서 나온 ‘백엔드 서비스도 정상 동작 중’이라는 부당 단정을 기존 근거 검사에 추가했다. ‘정상 동작 여부 미확인’은 허용한다. 이는 명시적 근거 검사의 보완이며 모든 의미 오류를 해결한 것은 아니다.

- 긴 근거 뒤에도 root가 전달한 정확한 현재 요청·목적을 다시 명시한다. 원문·등록 읽기와 인자 선택권은 유지한다. 이 문구만으로 반복 조회가 해결되었다고 주장하지 않는다.
- 복합 판단에medium/3072를 사용하는61 후보도 비교했으나,78.014초·66.974초 뒤 각각 길이 한도에 걸리고 전체214.444초 시간초과가 나서 철회했다.62는 검증한60의 실행 코드/추론 설정으로 복귀했다. 새 판단·권한·전체 시간 예산을 강제로 줄이지 않는다.

## 검증과 운영 범위
